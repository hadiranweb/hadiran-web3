# نقشه معماری اطلاعات و SEO — هادیران‌وب۳

وضعیت: **فاز A و B و برش ۱–۲ فاز C پیاده شده.** باقی‌ماندهٔ فاز C: OG تصویر اختصاصی (عمداً عقب افتاده).  
تاریخ: ۲۰۲۶-۰۹-۱۹  
منبع نسخهٔ محصول: ادغام نسخه ۱ (بازیابی + لندینگ) و نسخه ۲ (چت تمام‌صفحه + گراف موضوع)

---

## ۱. تصمیم‌های قفل‌شده

| تصمیم | مقدار | دلیل |
|---|---|---|
| صفحهٔ `/` | چت نسخه ۲ (رابط مکالمه‌ای) | محصول اصلی: شفاف‌سازی مسئله و هم‌فکری |
| لندینگ نسخه ۱ | **`/ecosystem`** | هب محصول؛ با `/hadiran` تداخل معنایی ندارد |
| هویت شخص | `/hadiran` می‌ماند | این صفحهٔ واقعی «دربارهٔ شخص» است؛ `/about` ساخته نمی‌شود |
| جزئیات موجودیت‌ها | از نسخه ۱ | صفحات `[slug]` برای ایندکس Google ضروری‌اند |
| چت‌بات | بازیابی متن نسخه ۱ + hop موضوع نسخه ۲ + جدول `messages` | کیفیت پاسخ + گراف دانش + قابلیت تاریخچه |
| هب موضوع | `/topics` + `/topics/[slug]` | پل بین سیلوها؛ نیت فرود موضوع ایندکس‌پذیر است |
| فیلتر `?topic=` | فقط UI همان لیست؛ کاننیکال مجموعه | چیپ و چت به هب می‌روند، نه به query |
| تماس | `/contact` = روش‌ها از `person.contactMethods` | بدون فرم پیام؛ همکاری همان `/lab/[slug]/collaborate` است |
| درایو ۱۵گیگ / LiveKit | **خارج از توپولوژی هادیران** | ساخته نمی‌شوند؛ با فاز C قاطی نمی‌شوند |

`/about` عمداً ساخته نمی‌شود. در SEO، `/about` یعنی سازمان/شخص. آن نقش را `/hadiran` دارد. لندینگ نسخه ۱ «اکوسیستم چیست و چهار جهان چگونه به هم وصل‌اند» است، نه بیوگرافی.

## ۲. اصول SEO که ساختار دایرکتوری از آن‌ها پیروی می‌کند

1. **یک URL = یک موجودیت = یک نیت جستجو.** صفحهٔ چت، صفحهٔ هب، صفحهٔ شخص، و صفحهٔ مقاله با هم رقابت نکنند (جلوگیری از cannibalization).
2. **سلسله‌مراتب پوشه = سلسله‌مراتب معنا.** مجموعه در ریشهٔ بخش، عضو در `[slug]`، زیرسند زیر همان عضو.
3. **عمق حداکثر سه سطح.** `/lab/[slug]/whitepaper` قابل قبول است. عمیق‌تر از این ایندکس و breadcrumb را خراب می‌کند.
4. **slug پایدار و لاتین.** UI فارسی است؛ URL انگلیسی/ترانسلیتریشن است (`what-is-web3` نه `وب۳-چیست`). ثبات لینک، کپی‌پذیری، و سازگاری ابزارها مهم‌تر از کلیدواژهٔ فارسی داخل مسیر است.
5. **محتوای اصلی با path، نه query.** فیلتر موضوع `?topic=` فقط فیلتر UI است؛ صفحهٔ مجموعهٔ موضوع اگر ارزش ایندکس دارد باید `/topics/[slug]` شود، نه تکیه به query.
6. **صفحهٔ کلاینت‌محور بدون پوستهٔ سرور ایندکس نمی‌شود.** `/` چت است، اما باید Server Component با H1، توضیح، و لینک‌های داخلی داشته باشد؛ ویجت چت Client است.
7. **سیلو (silo) با لینک داخلی.** هر جهان فقط از هب و از موجودیت‌های هم‌موضوع به جهان‌های دیگر پل می‌زند. فوتر و ناوبری همهٔ سیلوها را نشان می‌دهند؛ بدنهٔ مقاله نباید بی‌دلیل به همه جا لینک شود.
8. **Canonical یکتا، بدون duplicate.** لیست و جزئیات هر دو ایندکس می‌شوند؛ صفحهٔ فیلترشده با query `noindex` یا canonical به مجموعه می‌رود مگر اینکه صفحهٔ موضوع جدا ساخته شود.

## ۴. نقشهٔ پوشهٔ Next.js App Router

هر segment پوشه = یک URL. Route Group برای SEO دیده نمی‌شود و فقط برای سازمان کد است.

```

  sitemap.ts                          همهٔ صفحات موجودیت + مجموعه‌ها + /ecosystem + /hadiran
  page.tsx                            /  — Server Component: metadata + پوستهٔ ایندکس‌پذیر + <AIChat />
  ecosystem/
    page.tsx                          /ecosystem — لندینگ نسخه ۱ (آمار، معرفی، CTA)
  hadiran/
    page.tsx                          /hadiran
  signin/
    page.tsx                          /signin  (noindex — ورود OTP)
  knowledge/
    page.tsx                          /knowledge

      page.tsx                        /knowledge/new  (noindex — نوشتن، نیازمند نشست)

    [slug]/
      page.tsx                        /topics/[slug]

    page.tsx                          /contact  (روش‌های تماس؛ بدون فرم)
```

Route Group پیشنهادی برای خوانایی کد، بدون تغییر URL:

```
src/app/(site)/...     صفحات ایندکس‌پذیر
src/app/(chat)/page.tsx   اگر بخواهیم layout جدا برای چت — اختیاری
src/app/api/...
```

تا وقتی layout چت با بقیه یکی است، Route Group لازم نیست. اضافه کردن `(site)` فقط وقتی توجیه دارد که هدر چت با هدر صفحات محتوا فرق کند.

## ۶. صفحهٔ `/` — چت محصول، بدون خودکشی SEO

نسخه ۲ کل `page.tsx` را `"use client"` کرده. این برای Google تقریباً یک صفحهٔ خالی است.

الگوی اجباری:

```
src/app/page.tsx                 Server Component
  export const metadata = { title, description, openGraph, alternates.canonical }
  <h1> مسئله‌ات را بگو؛ با هم شفافش می‌کنیم </h1>
  <p> فضایی برای بازنمایی دقیق ایده‌ها و ساختاردهی به دغدغه‌ها. </p>
  <nav aria-label="بخش‌های اکوسیستم هادیران"> لینک /hadiran (درباره من) /knowledge /lab /courses /ecosystem </nav>
  <HomeChat />
```

قواعد:

- `metadata` فقط در Server Component تعریف می‌شود.
- H1 و یک پاراگراف واقعی در HTML اولیه باشد (نه فقط بعد از hydrate).
- JSON-LD `WebSite` با `potentialAction` از نوع `SearchAction` که `target` آن `/api/chat` نیست؛ برای موتور جستجو `target: {site}/knowledge?q={search_term_string}` — چت برای ربات قابل اجرا نیست.
- عنوان تب: `هادیران | فضای هم‌فکری، شفاف‌سازی مسئله و طراحی سیستم‌ها`
- توضیحات متا باید خودِ محصول را بگوید، نه لیست آمار. آمار مال `/ecosystem` است.

## ۷. صفحهٔ `/ecosystem` — لندینگ نسخه ۱

محتوای منتقل‌شده از `src/app/page.tsx` نسخه ۱:

- بج «رابط اصلی اکوسیستم» → بازنویسی شود به «نقشهٔ اکوسیستم» تا با `/` رقابت نکند
- H1 معرفی اکوسیستم (نه «مسئله‌ات را بگو» — آن H1 مال `/` است)
- چهار کارت آمار: دانش، پروژه، دوره، موضوع
- CTA: درباره من، ورود به آزمایشگاه، و **شروع هم‌فکری** → `/`
- ویجت چت روی این صفحه **نمی‌آید**؛ در غیر این صورت duplicate با `/`

Metadata پیشنهادی:

- title: `اکوسیستم هادیران‌وب۳ | دانش، آموزش، آزمایشگاه، هویت`
- description: توضیح مدل چهارجهانی و اتصال آن‌ها از طریق موضوع

Internal links اجباری از این صفحه: `/`, `/hadiran`, `/knowledge`, `/lab`, `/courses`

## ۸. سیلو و لینک داخلی

```
                    /ecosystem  (هب محصول)
                    /  (چت — دروازهٔ مکالمه)
                           |
          -----------------+-----------------
          |         |            |          |
     /hadiran  /knowledge      /lab     /courses
          |         |            |          |
          |    /knowledge/x   /lab/y    /courses/z
          |                      |
          |              /lab/y/whitepaper
          |
     موضوعات مشترک = پل بین سیلوها  →  /topics/[slug]  (جهان پنجم نیست)
```

قواعد لینک:

- از مقاله فقط به موضوع، پروژهٔ مرتبط، و دورهٔ مرتبط لینک بده (از join table)، نه به همهٔ دانشنامه.
- چیپ موضوع روی دانش / آزمایشگاه / دوره / شخص / حباب چت → **`/topics/[slug]`** نه `/knowledge?topic=`.
- از پروژه به اسناد همان پروژه و به نقش‌های همکاری.
- ناوبری سراسری (جهان‌ها): `/` ، `/ecosystem` ، `/hadiran` ، `/knowledge` ، `/lab` ، `/courses` — موضوع و تماس در **فوتر** می‌آیند، نه در نوار اصلی.
- Breadcrumb هر صفحهٔ `[slug]` باید مجموعهٔ والد را نشان دهد.

نمونه breadcrumb:

```
خانه / دانشنامه / پروتکل MCP
خانه / آزمایشگاه / کیت ابزار MCP / وایت‌پیپر
خانه / اکوسیستم
```

## ۹. Metadata، فایل‌های فنی، دادهٔ ساخت‌یافته

هر `page.tsx` ایندکس‌پذیر باید `generateMetadata` داشته باشد (پویا برای `[slug]`).

حداقل فیلدها:

- `title` یکتا، الگوی `عنوان صفحه | هادیران‌وب۳`
- `description` از `summaryFa` / `descriptionFa`
- `alternates.canonical` روی همین path
- `openGraph.url` + `og:type` مناسب (`website` / `article`)
- `robots` فقط روی collaborate: `{ index: false, follow: true }`

فایل‌های ریشه:

| فایل | نقش |
|---|---|
| `src/app/sitemap.ts` | تولید از DB: knowledge, projects, courses, documents, topics + URLهای ثابت (`/contact`، `/topics`) |
| `src/app/robots.ts` | `Allow: /` — `Disallow: /api/` — `Disallow: /*/collaborate` — `Disallow: /signin` — `Disallow: /knowledge/new` — `Disallow: /*/edit` — اشاره به sitemap |
| JSON-LD در layout | `Organization` / `Person` برای هادیران (یک‌بار) |
| JSON-LD در صفحهٔ موجودیت | مطابق جدول بخش ۵ |

`lang="fa"` و `dir="rtl"` در `<html>` می‌ماند. اگر نسخهٔ انگلیسی URL جدا شد، آن وقت `hreflang`؛ تا آن روز hreflang نگذارید (اشاره به زبانی که صفحه ندارد، خطا است).

## ۱۰. چت و تأثیرش روی ساختار دایرکتوری

چت URL جدا نمی‌گیرد. منطق پشت `/api/chat` می‌ماند تا مسیرهای محتوا تمیز بمانند.

ادغام منطق (برای فاز پیاده‌سازی کد، نه تغییر URL):

```
سؤال
  → نرمال‌سازی توکن نسخه ۱ (ارقام فارسی، حذف علائم)
  → مسیر الف: ILIKE وزن‌دار روی title/summary/body دانش، پروژه، دوره
  → مسیر ب: ILIKE روی topics سپس hop از knowledge_topics / project_topics / course_topics
  → اتحاد نتایج + امتیاز relevance
  → پاسخ قالبی از topها
  → ذخیره در conversations + messages (schema نسخه ۲)
```

خروجی API برای UI نسخه ۲ سازگار می‌شود:

```json
{
  "answer": "...",
  "references": {
    "knowledge": [{ "slug", "title", "summary" }],
    "projects":  [{ "slug", "name",  "summary" }],
    "courses":   [{ "slug", "title", "summary" }],
    "topics":    [{ "slug", "name" }]
  }
}
```

لینک‌های داخل حباب پاسخ باید دقیقاً به درخت بخش ۳ بروند (`/knowledge/[slug]` و غیره). اگر صفحهٔ جزئیات نباشد، چت به ۴۰۴ می‌رسد و سیگنال SEO خراب می‌شود — برای همین صفحات `[slug]` نسخه ۱ قبل از ادغام چت باید موجود باشند.

جدول `messages` محتوای ایندکس‌پذیر عمومی نیست. مکالمهٔ کاربر در sitemap نمی‌آید.

## ۱۱. فیلتر موضوع و duplicate content

نسخه ۲: `/knowledge?topic=uuid`  
نسخه ۱: `/knowledge?topic=slug`

تصمیم قفل‌شده (فاز C — **هب کاننیکال**):

- `/topics/[slug]` فرود ایندکس‌پذیر موضوع است (دانش + پروژه + دوره روی یک صفحه).
- چیپ موضوع و لینک چت به هب می‌روند، نه به query.
- `?topic=` فقط فیلتر UI همان مجموعه است (`/knowledge?topic=ai` دانش را تنگ می‌کند). کاننیکال آن URL همیشه `/knowledge` (یا `/lab` / `/courses`) می‌ماند.
- **ریدایرکت ۳۰۱ از `?topic=` به هب ممنوع است** — نیت فیلتر لیست با نیت هب گراف یکی نیست.
- این URLهای query از صفحات دیگر تبلیغ نمی‌شوند.

هرگز UUID در URL عمومی نگذارید.

### ۱۸.۶ پیشنهاد چندآزمونی — تعریف، نمره، درخت عارضه (قفل ساخت نیست)

هدف: هر تعداد آزمون از جنس casio-ss، بدون سرویس/DB/هویت جدا، بدون جهان پنجم، بدون Typeform.

سه لایهٔ جدا که قاطی نمی‌شوند:

| لایه | چیست | کجا |
|---|---|---|
| تعریف (pack) | نوشتار، بخش، سؤال، مقیاس، رضایت، نسخه | سند نسخه‌دار؛ نه جدول ردیف‌سؤال به‌عنوان منبع حقیقت |
| اجرا | فرم کاروسل، ذخیرهٔ پاسخ با شناسهٔ پایدار | `/analyzers/[slug]` + `analyzer_attempts` |
| معنا | فرمول نمره، ماتریس، درخت سؤال→عارضه→کلیدواژه | گراف داخل همان pack؛ موتور خالص بدون `eval` |

**Pack (یک JSON/YAML نسخه‌دار برای هر آزمون).** casio-ss اولین نمونه است. فیلدهای اصلی:

- `slug` پایدار لاتین، `version`، `status` (`draft` / `open` / `archived`)
- `scale` اعلامی (برای casio: کاشی گسستهٔ ۰–۱۰؛ نوع کنترل جدید فقط با افزودن صریح به رانر)
- `sections[]` → `items[]` با `id` پایدار (`FL.L1.Q1` نه شمارهٔ ردیف)
- `findings[]` (عارضه/لایه/بُعد): `id`، عنوان، والد اختیاری (درخت)
- `keywords[]`: برچسب گزارش/دانش؛ وکتور و Pinecone نیست
- `edges[]`: `from` سؤال یا عارضه → `to` عارضه یا کلیدواژه + `weight` + `transform` (`identity` / `reverse` / آستانه)
- `formulas[]`: اعلانی نه کد آزاد. عملگرها: `reverse`، `mean`، `sum`، `sum_div`، `weighted_sum`، `argmin`، `band`، `cap_if` (سؤال کلیدی سند ۰۵)، `matmul` (لیست تنک `(item, dimension, weight)`)

ماتریس پیچیده = همان یال‌های وزن‌دار، نه صفحهٔ اکسل در UI. مثال casio لایه: نمرهٔ لایه = مجموع مؤثر چهار سؤال ÷ ۲؛ گلوگاه = `argmin` پنج لایه.

**اجرا در برابر تألیف.** هب و عضو عمومی عوض نمی‌شوند. تألیف noindex است، فقط مالک، زیر `/workspace/analyzers` (نه `/admin`، نه `/signup`). عمق حداکثر سه: ویرایش نمره، **پاسخ‌ها** و **تفسیر اولیه** تب همان `/workspace/analyzers/[slug]` است نه مسیر چهارم. عضو بعد از ثبت فقط قالب خلاصه (`userSummaryTemplateFa` با `{پارامتر}`) را در `/analyzers/[slug]/report` می‌بیند؛ تفسیر لایه/گلوگاه و گیت سه‌رنگ ارزیابی برای آزمون‌ساز در تب‌های پاسخ‌ها و تفسیر اولیه است.

**دادهٔ اجرا (تعمیم `casio_attempts` وقتی دومین آزمون آمد):**

- `analyzer_attempts`: حساب، slug، version قفل‌شده، رضایت، answers jsonb، وضعیت
- بعد از submit: `analyzer_results` اسنپ‌شات نمره با همان version (گزارش کهنه بازتولیدپذیر)
- سؤال در DB ردیف نمی‌شود؛ پاسخ با id+version است (همان اصل سند ۰۲)

**صریحاً نه:** میکروسرویس، DB جدا، `eval`/JS کاربر، جنریتور PDF کپی‌شده، جایگزینی دانشنامه با وکتور، تغییر مقیاس casio به لایکرت/اسلایدر، CMS عمومی برای همه.

ترتیب ساخت: (۱) **انجام‌شده** pack تایپی + مهاجرت casio به pack بدون تغییر UI اجرا. (۲) **انجام‌شده** موتور نمرهٔ اعلانی (`src/lib/analyzers/score.ts`) طبق سند ۰۵؛ اسنپ‌شات روی `casio_attempts.results` در submit؛ به کاربر در فرم نشان داده نمی‌شود. (۳) **انجام‌شده** درخت سؤال→عارضه→کلیدواژه از ماتریس تفسیر + گزارش شخصی noindex در `/analyzers/casio-ss/report`؛ گیت سبز/زرد/قرمز در گزارش نیست. (۴) **انجام‌شده** تألیف مالک در `/workspace/analyzers` (noindex؛ تب نمره/گزارش روی همان `/workspace/analyzers/[slug]`). casio-ss بذر اولیه است و بعد از استقرار در `analyzer_packs` مثل بقیه از میز ویرایش می‌شود؛ پاسخ‌های casio همچنان `casio_attempts`.

## ۱۹. قرارداد هویت کاربر — `/signin` و `/account`

قفل این برش: **همان درِ موبایل، پروفایل نام، شناسهٔ ۸رقمی، ستون کانال رزرو.** ایمیل به‌عنوان ورود، ربات، OTP تازه، میکروسرویس، و استقرار پرود این برش نیستند.

### ۱۹.۱ نیت URL

| URL | نیت | ایندکس |
|---|---|---|
| `/signin` | ورود / ساخت حساب `member` با موبایل | **noindex** |
| `/account` | پروفایل صاحب نشست: نام، نام‌خانوادگی، شناسهٔ ۸رقمی | **noindex** |
| `/hadiran` | شخص هادیران | ایندکس — قاطی نشود |

ثبت‌نام جدا نیست. بار اول OTP حساب می‌سازد. `/signup` و `/profile` ساخته نمی‌شوند.

### ۱۹.۲ مدل داده

- کلید داخلی: `accounts.id` — در UI نشان داده نمی‌شود و رمز ورود نیست.
- ورود این برش: فقط `accounts.phone` + OTP/رمز موجود. ستون `phone` همچنان `NOT NULL UNIQUE`.
- نام: `accounts.given_name` و `accounts.family_name`. `display_name` از روی آن‌ها همگام می‌شود (برای casio-ss / IND.1).
- کانال رزرو روی **همان** `accounts`، بدون UI و بدون ورود: `email` + `email_verified_at`، `telegram_user_id` + `telegram_linked_at` (هر دو unique و nullable).
- شناسهٔ نمایشی: جدول `account_public_codes` (`account_id` → کد ۸رقمی تصادفی یکتا، بازهٔ ۱۰۰۰۰۰۰۰–۹۹۹۹۹۹۹۹). ورود با این کد نیست. بعد از ساخت حساب (و بک‌فیل حساب‌های موجود) اختصاص می‌یابد.

جدول `users` یا سرویس هویت جدا ساخته نمی‌شود. جدول `person` همان شخص هادیران است.

### ۱۹.۳ این برش می‌سازد / نمی‌سازد

| می‌سازیم | نمی‌سازیم |
|---|---|
| ستون نام + کانال رزرو روی `accounts` | ورود با ایمیل، جادویی، OAuth، پسکی |
| جدول `account_public_codes` | دادن `accounts.id` به کاربر |
| `/account` و لینک «حساب» در منوی نشست | `/signup`، میکروسرویس، OTP قالب تازه |
| مایگریشن `0009_account_profile` | ربات تلگرام، ادغام حساب، استقرار پرود این برش |

مالک: همان شماره + `HADIRAN_OWNER_PASSWORD` روی لیارا. کوکی host-only؛ `Domain=.hadiranweb.ir` نه.

دروازه روی **وضعیت فعلی حساب** است، نه فقط ثبت‌نام اول. بک‌فیل `0010` دیگر کافی نیست.

### ۱۹.۶ پیش‌نویس فیلد — رفرش بدون پاک‌شدن تایپ

## ۲۰. ربات‌ها — میز کار مالک

هدف این برش: **تنظیم و اتصال** رباتی که مالک در کانال ثالث می‌سازد. تارگت اول: **تلگرام**. ورود سایت با تلگرام روشن نمی‌شود (`accounts.telegram_user_id` همچنان رزرو است).

### ۲۰.۱ نیت URL

| URL | نیت | ایندکس |
|---|---|---|
| `/workspace/bots` | فهرست ربات‌های مالک | **noindex** |
| `/workspace/bots/new` | ساخت رکورد | **noindex** |
| `/workspace/bots/[id]` | تنظیم + اتصال توکن + انتخاب آزمون | **noindex** |
| `/api/bots/telegram/[id]/webhook` | دریافت Update از تلگرام | API |

عمق میز حداکثر سه. `/admin` ساخته نمی‌شود. نوار اصلی سایت لینک ربات ندارد.

### ۲۰.۲ اتصال تلگرام

از Bot API رسمی، نه کتابخانهٔ polling:

- تأیید توکن: `getMe`
- ثبت آدرس: `setWebhook` با `secret_token` و `allowed_updates: message, callback_query`
- تشخیص سلامت: `getWebhookInfo`
- قطع: `deleteWebhook`
- **نه** `getUpdates` (با وب‌هوک جمع نمی‌شود)

آدرس وب‌هوک: `https://hadiranweb.ir/api/bots/telegram/[id]/webhook` (از `NEXT_PUBLIC_SITE_URL`). فقط HTTPS عمومی. هدر `X-Telegram-Bot-Api-Secret-Token` با مقایسهٔ زمان‌ثابت.

خروجی سرور ایران به `api.telegram.org` مسدود است و ورودی تلگرام→مبدأ ایرانی اغلب `Connection timed out` است. برنامه با `TELEGRAM_API_BASE` (لیارا، نه GitHub) به Cloudflare Worker می‌زند: `/bot…` به Bot API، `/hook/<botId>` به وب‌هوک هادیران. `getUpdates` نیست.

توکن BotFather در گیت/چت/پاسخ API بعد از ذخیره نیست؛ در Postgres به‌صورت AES-GCM با کلید مشتق از `HADIRAN_JWT_SECRET` (لیارا، نه GitHub).

### ۲۰.۳ گفتگوی آزمون در تلگرام

وب‌هوک بعد از ACK، آزمونِ انتخاب‌شدهٔ ربات را سؤال‌به‌سؤال جلو می‌برد (پیش‌فرض `casio-ss`). `/start` معرفی + رضایت؛ `/help` راهنما؛ `setMyCommands` هنگام اتصال. رضایت pack اجباری است؛ شماره با دکمهٔ تماس تلگرام (شمارهٔ خود کاربر). حساب عضو با همان موبایل ساخته/وصل می‌شود؛ `telegram_user_id` فقط پیوند ربات است — ورود سایت با تلگرام روشن نمی‌شود و JWT/کوکی از وب‌هوک صادر نمی‌شود. پاسخ‌ها در `casio_attempts` / `analyzer_attempts` همان حساب. مقیاس ۰ راست ۱۰ چپ. گیت سبز/زرد/قرمز در چت نیست.

صریحاً نه: میکروسرویس ربات، ورود تلگرامی، `getUpdates`، توکن در GitHub Secret، Typeform، نمایش توکن کامل پس از ذخیره.

## ۲۱. نقش آزمون‌ساز، کد معرف، کد تخفیف

چهار نقش: **مهمان** (بی‌نشست)، **عضو** (`member`)، **آزمون‌ساز** (`author`)، **مدیر** (`owner`). `/admin` و `/dashboard` ساخته نمی‌شود. آزمون‌ساز فقط `/workspace/analyzers` (+ معرفی‌های خودش). ربات، فروشگاه، ثبت دانش مال مدیر است.

### ۲۱.۱ نیت URL

| URL | نیت | ایندکس |
|---|---|---|
| `/workspace/analyzers` | فهرست آزمون‌های قابل‌دسترسی | **noindex** |
| `/workspace/analyzers/[slug]` | ویرایش/پاسخ/اعطا روی همان صفحه | **noindex** |
| `/workspace/referrals` | کسانی که کد این حساب را زده‌اند | **noindex** |
| `/workspace/network` | درخت معرف کل سایت (فقط مدیر) | **noindex** |
| `/workspace/discounts` | کد تخفیف (فقط مدیر) | **noindex** |

عمق حداکثر سه. اعطا تب همان ویرایش است نه مسیر چهارم.

### ۲۱.۲ کدها

- **کد معرف = شناسهٔ ۸رقمی حساب.** ورود با آن نیست. هر نقش یک کد دارد چون هر نقش یک حساب دارد.
- درخت حساب: `accounts.referred_by_account_id`؛ اولین تماس می‌ماند؛ خودمعرفی و حلقه ممنوع.
- معرف روی تلاش: `referrer_account_id` در `casio_attempts` / `analyzer_attempts` (اختیاری، جدا از درخت حساب).
- **کد تخفیف جداست** (حروف/رقم، نه ۸رقم خالص). کمپین است نه آدم: درصد یا مبلغ، سقف، دامنه `any` / `analyzer` / `shop`. زرین‌پال نیست.

### ۲۱.۳ دسترسی آزمون

`analyzer_packs.created_by` + `analyzer_grants`. مدیر همه را می‌بیند. آزمون‌ساز: ساختهٔ خودش یا اعطاشده. اعطا نقش `member` را `author` می‌کند؛ `owner` را پایین نمی‌آورد.

صریحاً نه: کد معرف روی هر ردیف، عوض کردن معرف بعد از ثبت، ورود تلگرامی، چندفروشنده.
