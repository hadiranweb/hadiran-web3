# مرکز سفارش و گزارش تسویه — مرحلهٔ ۵

نسخهٔ داخلی آمادهٔ بازبینی؛ بدون استقرار، انتقال Drive، کیف پول، درگاه یا استرداد واقعی.

## تصمیم‌های تأییدشده

کاربر صریحاً نمایش **تومان** با حفظ محاسبه/ذخیرهٔ **IRR**، و دوره‌های **شمسی / Asia/Tehran** را انتخاب کرد. تبدیل IRR÷۱۰ دقیق است؛ یک ریال به صورت ۰٫۱ تومان نمایش می‌یابد، نه گردکردن پنهان. جمع‌های SQL به صورت رشتهٔ صحیح و قالب‌بندی با BigInt هستند. واحدهای دیگر تبدیل یا با IRR جمع نمی‌شوند. در جزئیات، مقدار ذخیره‌شده نیز صریحاً در دسترس است.

## مسیر و مجوز

| صفحه | API خواندن | دامنه |
|---|---|---|
| `/workspace/shop/orders` | `/api/workspace/shop/orders` | فقط owner، دامنهٔ مدیریتی سراسری موجود |
| `/workspace/finance` | `/api/workspace/finance` | فقط owner، سفارش settled بر اساس settledAt |
| `/account/purchases` | `/api/account/purchases` | فقط buyer_id نشست؛ query نمی‌تواند حساب را عوض کند |

لینک از فروشگاه و حساب افزوده شده و گزارش در سایدبار مدیر است. نقش author یا grant آزمون مجوز گزارش مالی نمی‌دهد. owner چندسازمانی/tenant-scoped معرفی نشده است. صفحات جزئیات موجود و endpointهای نوشتن قبلی حفظ شده‌اند.

APIها خصوصی/no-store و فقط GET هستند؛ فهرست ۲۰تایی با ترتیب پایدار تاریخ/شناسه و شمار کامل. snapshot خواندن در تراکنش repeatable-read/read-only است. خطا/نبود DB: `total/asOf=null` و بدون مبلغ جایگزین، نه صفر و نه نمونه. خطای فیلتر 400، عدم نشست 401، عدم مجوز 403 و زیرساخت ناموجود 503.

## فیلتر و تعریف عدد

`period=month|previous|all|custom`، `from/to=YYYY-MM-DD` شمسی، `basis=created|settled`، `state` از پنج مقدار موجود، `product` شناسه یا اسلاگ واقعی، `currency` واحد ذخیره‌شده، `q` عنوان/شمارهٔ سفارش، `page` محدود به ۱ تا ۱۰۰۰۰. بازهٔ custom هر دو تاریخ را می‌خواهد و حداکثر حدود یک سال است؛ تاریخ ناممکن/اسفند غیرکبیسه رد می‌شود.

«تا» شامل آن روز محلی است و به `[startOfDay(from),startOfDay(dayAfterTo))` در UTC تبدیل می‌شود. مرز روز با Intl و جست‌وجوی تاریخ واقعی پیدا می‌شود، نه offset ثابت؛ گپ نیمه‌شب DST تاریخی نیز تست شده است. دورهٔ گزارش مستقل از زبان UI شمسی باقی می‌ماند.

در گزارش، state=settled و basis=settled سمت سرور ثابت‌اند. تاریخ ثبت سفارش نمی‌تواند جای تاریخ تسویه بنشیند؛ شمارهٔ پیگیری وصول نیست و مجموع تسویه سود خالص نیست. سفارش تسویه‌شدهٔ بدون زمان، در گزارش بازه‌دار زمان تسویه وارد نمی‌شود؛ شمار آن صریح است. all-time شامل همین رکوردهای بی‌تاریخ نیز هست و زمان فرضی نمی‌سازد.

در مرکز سفارش، مبلغ، جمع **همهٔ سفارش‌های فیلترشده** است؛ نه ادعای وصول. کارت‌های وضعیت، سایر فیلترها را رعایت و فیلتر خود وضعیت را نادیده می‌گیرند تا facet قابل انتخاب باشند. مبلغ و تخفیف از snapshot سفارش خوانده می‌شوند، نه قیمت جاری محصول. کارت هر واحد به همان فیلتر و همان واحد برمی‌گردد و با سفارش‌های مبدأ تطبیق دارد. «دسترسی محصول» وجود entitlement همان buyer/product را نشان می‌دهد؛ الزاماً صدور تازه از همین سفارش نیست.

فهرست قدیمی فروشگاه همچنان فقط ۴۰ سفارش اخیر است؛ عنوان/پیام آن محدودیت را روشن می‌کند و صف کامل به مرکز جدید پیوند دارد. مرکز جدید شمارش از زیرمجموعهٔ ۴۰تایی نمی‌سازد.

## ثبت حساس و اتمیک‌بودن

- ساخت/بازیابی سفارش با advisory transaction lock برای buyer/product؛ retry هم‌زمان سفارش موازی تازه نمی‌سازد. دادهٔ تاریخیِ احتمالاً تکراری خودسرانه ادغام/حذف نمی‌شود.
- snapshot قیمت/واحد/تخفیف/مقصد، مصرف تخفیف و رویداد ساخت در همان تراکنش‌اند. خواندن کد تخفیف در مسیر shop با row lock انجام می‌شود؛ پرشدن ظرفیت سفارش ناقص باقی نمی‌گذارد. helper مشترک executor اختیاری دارد؛ رفتار پیش‌فرض سایر مصرف‌کنندگان عوض نشده و اتمیک‌بودن مسیر آزمون از این نتیجه استنباط نمی‌شود.
- ثبت پیگیری، لغو، تأیید و رد با `FOR UPDATE` روی سفارش و کنترل صاحب عملیات‌اند. actor از نشست و حساب فعال سرور می‌آید؛ بدنهٔ درخواست نمی‌تواند آن را تعیین کند.
- تأیید: state، settledAt، entitlement یکتا و رویداد همگی commit یا rollback می‌شوند. درخواست تکراری تأیید موفق، زمان/رویداد/دسترسی را تکرار نمی‌کند. رقابت تأیید/رد فقط یک برنده دارد.
- پیگیری تکراری همان مقدار و لغو/رد تکراری همان وضعیت idempotent هستند. تغییر متعارض همچنان 409 می‌دهد. شمارهٔ پیگیری بدون تأیید دسترسی نمی‌دهد.
- تأیید دوبارهٔ سفارش قدیمی settled با entitlement مفقود، در backend همان endpoint، دسترسی را یک بار ترمیم می‌کند؛ مبلغ یا زمان تسویهٔ تاریخی بازنویسی نمی‌شود. ترمیم گروهی/خودکار یا ابزار جداگانهٔ ترمیم ساخته نشده است.

`0021_shop_order_events.sql` فقط جدول رویداد و indexهای خواندن را اضافه می‌کند؛ ۲۲ migration قبلی دست‌نخورده‌اند. manifest زمان شروع نیز از SQL بازتولید و تطبیق بایتی شده است. migration محلی اعمال و اجرای مجدد بدون تغییر بود.

رویداد شامل عامل، نقش زمان عملیات، قبل/بعد وضعیت و زمان UTC است. تاریخچهٔ قدیمی backfill جعلی ندارد؛ جزئیات حداکثر ۵۰ رویداد آخر را با زمان تهران نشان می‌دهد. نام از حساب فعلی خوانده می‌شود، نه ادعای نام تاریخی. مدیر عامل را می‌بیند؛ عضو فقط اطلاعات خودش و عنوان کلی مدیر را دریافت می‌کند، نه شناسهٔ داخلی/کد مدیر دیگر. این log عملیاتی از مسیر برنامه افزایشی است؛ نه دفتر مالی متوازن، سند تطبیق بانکی یا تضمین ضد‌دست‌کاری در برابر مدیر DB.

## مرز دامنهٔ باقی‌مانده

**رابط واقعی سفارش ↔ آزمون در مدل فعلی وجود ندارد**؛ shop فقط digital/physical/course دارد. فیلتر آزمون از تشابه نام، buyer یا نوبت آزمون جعل نشده است. افزودن چنین فیلتری نیازمند تصویب اتصال واقعی خرید آزمون به سفارش/حق استفاده است و به‌عنوان مورد باز مرحله ثبت می‌شود. فیلتر محصول اکنون واقعی و فعال است.

اصل صفحهٔ خانه، پرتره، HomeChat، theme، گراف معرف، API قدیمی گراف و مجوزهای آزمون محفوظ‌اند. تغییر برچسب settled از «دسترسی باز است» به «تسویه‌شده» ادعای نادرست دربارهٔ legacy بدون entitlement را حذف می‌کند؛ وضعیت‌های backend همان پنج مقدار هستند.

## آزمون و بازتولید

```sh
npm run typecheck
npm run lint
npm run build
node qa/finance_unit.cjs
node qa/finance_api.cjs
PYTHONPATH=/tmp/hadiran-qa PLAYWRIGHT_BROWSERS_PATH=/home/user/.cache/pw-browsers python qa/finance_browser.py
python qa/sync_latest_preservation.py
```

- ۹ گروه API واقعی: مجوزها، بازهٔ شمسی/تهران و reconciliation، صفحه‌بندی/حریم خریدار، retry هم‌زمان ساخت/پیگیری/تأیید، rollback خرابی grant و audit، ترمیم idempotent، رقابت ظرفیت تخفیف و rollback مصرف، رقابت تأیید/رد، snapshot قیمت/واحد و جمع بزرگ/عامل نشست.
- ۶ گروه unit: کبیسه/نوروز/DST، انتهای شامل و شروع ماه/سال، BigInt و اعشار تومان، parser و اجبار scope گزارش، نبود DB/خطای تزریق‌شده، تطابق هر ۲۳ migration با فایل SQL.
- ۷ گروه مرورگر، ۷۲ حالت owner در FA/EN روشن/تاریک و ۳۲۰ تا ۱۹۲۰؛ متن ۲۰۰٪، تاریخچهٔ عضو، جزئیات/برگشت، فیلتر نامعتبر، reduced-motion و نبود واقعی DB. فقط یک POST صریح تأیید در مرورگر؛ مرور گزارش/فیلتر/صفحه‌بندی هیچ نوشتن مالی ندارد؛ صفر خطای JS/hydration یا HTTP 5xx در آزمون عادی مرورگر.
- برگشت‌پذیری: گراف ۷ API + ۷ گروه مرورگر/۷۲ layout؛ خانه‌های نقش‌محور ۷ API + ۷ گروه مرورگر/۸۴ layout؛ نمونهٔ P02 با ۱۰۸ حالت؛ قرارداد قدیمی شبکه، ۱۲ گروه preservation و ۸ گروه pure/worker نیز موفق‌اند.

همهٔ این نتایج روی PostgreSQL **محلی QA** است. خطاهای عمدی 500 فقط برای اثبات rollback در DB نام‌دار آزمایشی تزریق و triggerها حذف شدند. فایل‌های cookie آزمون فقط در cache مستثنا از snapshot ذخیره می‌شوند. اعداد/نام‌ها در تصاویر آزمایشی‌اند و فروش محیط اصلی نیستند. این آزمون، اثبات اتصال به DB تولید یا تأیید وصول پول واقعی نیست.
