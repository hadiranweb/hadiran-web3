# مدل دامنهٔ محصول، خدمت و عامل‌های هادیران

تاریخ: ۲۰۲۶-۱۱-۰۷
وضعیت: **تصمیم‌های دامنهٔ آزمون و اشتراک تثبیت شده‌اند؛ اعداد پلن و قرارداد runtime بیرونی هنوز بازند**
دامنه: خدمات آزمون‌سازی و آزمون‌های مورد بحث، خدمات عامل/RAG، کاتالوگ، سفارش، دسترسی و اجرا.

> این سند برای تثبیت واژگان و روابط است؛ کد، schema، migration یا قواعد مالی را تغییر نمی‌دهد. migration را کاربر اجرا می‌کند. قواعد مالی مصوب محفوظ می‌مانند؛ ترتیب F01 نسبت به مدل مالی از قیدهای موجود کاربر پیروی می‌کند و این سند آن را بازتعریف یا جابه‌جا نمی‌کند.

## ۱. تصمیم معماری در یک نگاه

هادیران لازم نیست بین SaaS و AaaS یکی را انتخاب کند:

- **هادیران به‌عنوان محصول اصلی:** یک پلتفرم SaaS چندمستأجری برای ساخت، انتشار، خرید و اجرای خدمات.
- **عامل‌های منتخب:** می‌توانند بعداً به‌صورت Agent-as-a-Service عرضه شوند؛ خریدار یک کار را می‌سپارد و نتیجهٔ تعریف‌شده تحویل می‌گیرد.
- **مدل‌ها و قابلیت‌های پایه:** اگر خودِ دسترسی به مدل یا inference فروخته شود، آن بخش به AI-as-a-Service (AIaaS) نزدیک‌تر است.
- **بازارگاه:** سازندگان می‌توانند محصولات/خدمات خود را عرضه کنند؛ یک حساب می‌تواند در یک معامله خریدار و در معامله‌ای دیگر سازنده باشد.

«AaaS» اصطلاح یکنواخت و بی‌ابهامی نیست؛ در این سند آن را مشخصاً **Agent-as-a-Service** می‌گیریم و برای دسترسی به مدل/توان محاسباتی از **AIaaS** استفاده می‌کنیم. هادیران می‌تواند SaaSِ پلتفرم باشد و روی همان پلتفرم، بعضی Agentها را به‌صورت AaaS بفروشد.

**API داشتن هر خدمت، به‌تنهایی به معنی microservice بودن آن نیست.** هر دامنه باید API/رابط قراردادی روشن داشته باشد؛ در مرحلهٔ فعلی این مرزها می‌توانند در یک برنامهٔ ماژولار Next باشند. جداسازی runtime به سرویس‌های مستقل، تصمیم جداگانه و وابسته به نیاز است.

## ۲. واژگان پایه

| مفهوم | معنی در هادیران |
|---|---|
| **خدمت (Service)** | قابلیت کسب‌وکاری با قرارداد ورودی/خروجی و سیاست اجرا؛ ممکن است API داخلی یا endpoint راه‌دور داشته باشد. |
| **محصول (Product)** | چیزی که به خریدار عرضه می‌شود؛ مثلاً پلن آزمون‌ساز یا عرضهٔ یک آزمون. |
| **عرضه / Offer** | شرایط خرید محصول: یک‌باره، اشتراکی، سهمیه‌ای، مصرفی یا بسته‌ای. «پلن» یکی از شکل‌های عرضه است، نه مترادف همهٔ محصولات. |
| **قابلیت (Feature)** | عملی که سامانه می‌تواند انجام دهد، مثل `assessment.authoring` یا `assessment.interpretation`. |
| **دسترسی (Entitlement)** | حق مؤثر یک حساب برای استفاده از قابلیت، روی دامنهٔ مشخص، در مدت یا سهمیهٔ مشخص. خرید لزوماً نقش حساب را تغییر نمی‌دهد. |
| **مصرف (Usage)** | رویداد قابل شمارش، مانند شروع یک اجرای آزمون یا اجرای یک Agent. |
| **تحویل (Fulfillment)** | خروجی دامنه‌ایِ خرید: اجرای آزمون، نتیجه، تفسیر، سند یا نتیجهٔ Agent. |
| **جریان کار (Workflow)** | گراف نسخه‌دار از گره‌های دارای قرارداد که فراخوانی‌ها و تصمیم‌ها را به هم وصل می‌کند. |
| **Agent** | تعریفِ وظیفه‌محور شامل دستورها، ابزارهای مجاز، RAGهای مجاز و سیاست اجرا؛ می‌تواند یک Workflow را اجرا کند. |
| **RAG / پایگاه دانشی** | منبع بازیابی نسخه‌دار با مالکیت، دیده‌شدن و سیاست دسترسی مستقل؛ جزء بافت Agent است، نه مجوز دسترسی عمومی. |
| **MCP** | مرز استانداردِ ابزار/منبع برای مصرف‌کننده‌ها؛ محصول و چرخهٔ حکمرانی جداگانهٔ خود را دارد و با Agent یا Workflow یکی نیست. |

## ۳. ستون فقرات تجاری مشترک

ساختار مشترک باید معنای خرید و دسترسی را یکسان کند، اما جزئیات دامنه را در رکوردهای نوع‌دار نگه دارد:

```text
Account
  ├── Product / Marketplace listing
  ├── Offer / Price version
  ├── Order
  │     └── Order line (snapshot محصول، عرضه، قیمت، فروشنده و دامنهٔ خرید)
  ├── Payment / financial events / ledger
  ├── Entitlement grant (قابلیت، دامنه، سهمیه، زمان، منبع اعطا)
  ├── Usage event (مصرفِ idempotent و قابل حسابرسی)
  └── Fulfillment (خروجیِ نوع‌دارِ دامنه)
```

### اصول رابطه‌ها

1. **کاتالوگ مشترک، جزئیات نوع‌دار:** یک هویت/قرارداد مشترک برای محصولات و عرضه‌ها مناسب است؛ اما پلن آزمون‌ساز، محصول آزمون، کالای فروشگاه و Agent باید جزئیات دامنه‌ای نوع‌دار داشته باشند. از یک جدول بزرگِ پر از ستون‌های nullable یا یک `type + arbitrary resource_id` بدون اعتبارسنجی FK پرهیز شود.
2. **قیمت و خرید snapshot می‌شوند:** سفارش باید هویت عرضه و نسخهٔ قیمت/سیاستِ زمان خرید را ثبت کند؛ ویرایش بعدی کاتالوگ، سفارش تاریخی را بازنویسی نمی‌کند.
3. **پرداخت قبل از دسترسی مؤثر:** دسترسی از رویداد معتبر سفارش/پرداخت یا اعطای صریحِ مجاز ساخته می‌شود؛ نمایش یک کارت در UI خودش دسترسی نیست.
4. **داشبورد projection است:** داشبورد خدمت‌های فعال، سهمیهٔ باقی‌مانده و خروجی‌های قابل‌دسترسی را از Entitlementها و Usage می‌خواند؛ منبع حقیقت را دوباره در فیلدهای حساب کپی نمی‌کند.
5. **نقش با خرید یکی نیست:** نقش، مجوز کلی هویت است؛ Entitlement مجوز استفاده از محصول/قابلیت است. خرید پلن آزمون‌سازی به‌خودی‌خود نباید `account.role` را به `author` یا نقش بالاتری تبدیل کند.
6. **پیوند دامنه‌ای باید قابل‌اعتبارسنجی باشد:** جایی که FK ممکن است، شناسهٔ polymorphic آزاد مثل `(kind, id)` به‌تنهایی کافی نیست؛ fulfillmentهای آزمون، سند و Agent از extensionهای نوع‌دار استفاده کنند.

## ۴. مدل آزمون‌ساز و بازارگاه آزمون

### سمت سازنده

- خدمت نمایشی مناسب: **«پلن آزمون‌ساز»** اگر دوره/سهمیه دارد؛ **«دسترسی ابزار آزمون‌سازی»** اگر فقط مجوز استفاده است.
- کلید قابلیت مفهومی: `assessment.authoring`.
- عرضهٔ فعلی: **اشتراک دوره‌دار با سهمیهٔ ساخت آزمون**؛ هر listing پلن، تعداد ساخت، مدت معتبر و سیاست تمدید را صریح و قابل‌تنظیم نگه می‌دارد. تا وقتی این مقادیر و قیمت معتبر ثبت/فعال نشده‌اند، پلن فروش‌پذیر نیست؛ مقدار نامشخص صفر، رایگان، نامحدود یا سیاست تمدید پیش‌فرض فرض نمی‌شود.
- سفارش اشتراک از مسیر فروشگاه موجود می‌گذرد؛ زمان و مقدار پلن در سفارش snapshot می‌شوند و اشتراک فقط پس از تأیید دریافت آغاز می‌شود و سیاست تمدیدِ هر پلن به‌صراحت «شروع فوری» یا «شروع پس از پایان اشتراک جاری» است. سهمیه هنگام ساخت pack تازه، در تراکنش همان ساخت، یک واحد کم می‌شود؛ ویرایش pack مصرف تازه ندارد. مالک فعلی از گیت سهمیه مستثناست.
- صفحه و کنترل‌های سازنده در `/workspace` می‌مانند؛ خرید Entitlement نیست که نقش حساب را تغییر دهد و نقش/مجوزهای مدیریتی جدا هستند.

### سمت خریدار

محتوای آزمون و عرضهٔ فروش آن دو مفهوم‌اند:

```text
Analyzer/Assessment definition (pack + version + creator)
    └── Offer: اجرای یک نوبت + نتیجهٔ پایه (یک قیمت، یک‌بار برای همان اجرا)
          ├── Offer مستقل: تفسیر
          └── Offer مستقل: سند
```

اجرای قیمت‌دار فقط برای آزمون‌سازهای عمومیِ غیر-Casio است؛ Casio مرز خودش را حفظ می‌کند. هر آزمون‌ساز می‌تواند تعرفهٔ فعال و کامل خودش داشته باشد. بدون تعرفهٔ مثبت و تنظیم مالی کامل، اجرا/افزونه فروش‌پذیر نیست و به‌معنای خدمت رایگان هم نیست. نتیجهٔ همان اجرا جداگانه دوباره شارژ نمی‌شود.

### جلوگیری از صورتحساب تکراری

قاعدهٔ محصول قطعی است: **یک اجرای واحد، شامل نتیجهٔ پایه، فقط یک‌بار هزینه دارد.** سهمیهٔ اشتراک آزمون‌ساز دربارهٔ ساخت pack است و جایگزین یا bundle قیمت اجرای آزمون نیست. تفسیر و سند دو عرضهٔ مستقل و per-attempt باقی می‌مانند؛ قواعد مالی یا قیمت جدید از این تصمیم استنتاج نمی‌شود.

## ۵. پشتهٔ Workflow، Agent و RAG

### ۵.۱ دو صفحهٔ معماری، یک تجربهٔ واحد

```text
Control plane — داخل تجربهٔ هادیران، زیر /workspace
  رجیستری خدمات، سازندهٔ workflow، تعریف Agent، پیوند RAG/MCP، نسخه‌ها، سیاست‌ها
                │
                ▼
Execution plane — اجرای واقعیِ مجاز و قابل‌مشاهده
  APIهای ماژول‌های هادیران + runtimeهای راه‌دورِ تأییدشده + لاگ اجرا و مصرف
```

«در پشتهٔ سایت بودن» یعنی مالکیت تعریف، سیاست، نسخه، دسترسی و مشاهده‌پذیری از هادیران کنترل شود؛ لزوماً به معنی اجرای مدل سنگین، پایگاه برداری یا worker داخل process وب Next نیست.

### ۵.۲ الگوی شبیه n8n که ارزش اقتباس دارد

- workflow یک **گرافِ گره‌ها و اتصال‌ها** است؛ هر گره یک API/عملیات با ورودی و خروجی schemaدار است.
- گردش کار نسخهٔ `draft` و نسخهٔ `published` دارد؛ فقط نسخهٔ منتشرشده endpoint تولیدی می‌گیرد. هر اجرای قبلی به نسخهٔ دقیق خود ارجاع می‌دهد.
- هر اجرا شناسه، حساب/مستأجر، نسخهٔ workflow، وضعیت، زمان، خروجی مجاز، خطا و واحد مصرف دارد.
- مجوزهای ساخت، ویرایش، انتشار و اجرا مستقل‌اند و در سطح پروژه/منبع کمینه‌گرا اعمال می‌شوند.
- Credential و secret فقط سمت سرور و با مرجع امن نگه‌داری می‌شود؛ مقدار خام وارد graph، مرورگر، لاگ یا Git نمی‌شود.
- گره‌ها از فهرست کنترل‌شده و schemaدار انتخاب می‌شوند؛ کد دلخواه/`eval` مسیر پیش‌فرض نیست.
- قرارداد هر گره دست‌کم `serviceId`, `version`, `inputSchema`, `outputSchema`, scope دسترسی، timeout، idempotency و رفتار خطا را تعریف می‌کند.

این یک الهام از مدل n8n است؛ **استفاده از خود n8n یا افزودن وابستگی به آن تصمیم گرفته نشده است.** مستندات n8n هم Workflow را مجموعهٔ گره‌های متصل می‌داند، انتشار را از پیش‌نویس جدا می‌کند، execution را به‌عنوان یک اجرای نسخه‌دار ثبت می‌کند و دسترسی پروژه/اعتبارنامه را سطح‌بندی می‌کند. [مفاهیم Workflow در n8n](https://docs.n8n.io/key-concept-glossary) · [API نسخه‌های Workflow](https://docs.n8n.io/connect/n8n-api/workflow) · [نقش‌های پروژه](https://docs.n8n.io/administer/manage-users-and-access/set-permissions-and-roles-rbac/organize-work-in-projects)

### ۵.۳ موجودیت‌های کنترلی مفهومی

| نوع | مسئولیت |
|---|---|
| `service_definition` | شناسهٔ پایدار، مالک، نسخهٔ API، schemaها، نیازمندی دسترسی و وضعیت انتشار. |
| `workflow_definition` | گره‌ها، اتصال‌ها، triggerها، نسخهٔ draft/published و سیاست اجرای workflow. |
| `agent_definition` | هدف، دستورهای نسخه‌دار، مدل/ارائه‌دهندهٔ مجاز، ابزارهای مجاز، ارجاع RAG، سیاست خروجی/تأیید انسانی. |
| `knowledge_base` | مالک و tenant، منابع، نسخهٔ محتوا/ایندکس، سطح دیده‌شدن و سیاست retrieval. |
| `execution` | اجرای یک نسخهٔ دقیق از service/workflow/agent، حساب فراخوان، وضعیت، مصرف و نتیجهٔ حسابرسی‌شده. |
| `credential_reference` | شناسه/مرجعِ سکرت و scope آن؛ نه متن سکرت داخل graph یا pack. |

RAG تنها با مجوز صریح از اسنادی retrieve می‌کند که فراخوانی‌کننده حق دیدنشان را دارد. عمومی/داخلی/خصوصی بودن منبع به‌صورت سیاست مستقل ثبت می‌شود؛ Agent به‌صورت ضمنی به همهٔ منابع یا ابزارها دسترسی پیدا نمی‌کند.

### ۵.۴ مرز MCP

MCP بخشی از این پشته است، ولی با تعریف Agent یا workflow یکی نیست:

- سرویس MCP، رجیستری و تنظیمات مستقل خودش را حفظ می‌کند؛ سرور راه‌دور از ابتدا پشتیبانی می‌شود و نسخهٔ پروتکل مصوب `2025-11-25` است.
- Agent می‌تواند فقط از MCPهای تأییدشده و از طریق binding مجاز استفاده کند.
- انتشار، دیده‌شدن، سیاست امنیتی و تنظیمات هر MCP باید مستقل و مؤثر باشد؛ MCP به اتصال پیش‌فرض همهٔ workflowها تبدیل نمی‌شود.
- طرح موجود MCP در `docs/mcp-service-architecture-2026-10-22.md` مرجع این مرز است؛ این سند آن را جایگزین نمی‌کند.

### ۵.۵ محدودیت اجرا/ذخیره‌سازی

- control plane و سیاست‌ها در تجربهٔ هادیران قرار می‌گیرند؛ runtime می‌تواند API داخلی یا worker/سرویس بیرونی باشد.
- فرض فعلی این است که RAG/runtime/agent ممکن است روی یک سرویس جداگانه (احتمالاً همان Liara) اجرا شود؛ این فقط فرض معماری است. تا ارائهٔ قرارداد endpoint، احراز هویت، payload، timeout، خطا، idempotency و retention، هادیران هیچ endpointی را حدس نمی‌زند و هیچ فراخوانی بیرونی انجام نمی‌دهد.
- Agent در فاز فعلی فقط داخلی و تحت کنترل مالک است؛ مالک فعلی همان کاربر است. عمومی‌سازی، فروش مصرفی یا دسترسی عضو/سازندهٔ دیگر خاموش می‌ماند تا سیاست‌ها و قرارداد جداگانه تصویب شوند. چون قرارداد بیرونی مشخص نیست، در این برش adapter اجرایی/درخواست شبکه‌ای تازه‌ای اضافه نشده است؛ اتصال عمداً fail-closed می‌ماند.
- طبق قید موجود، مدل‌های `300M+` و زیرساخت برداری روی Liara قرار نمی‌گیرند. ارائه‌دهنده و محل اجرای RAG/vector جداگانه و هنوز انتخاب‌نشده است؛ این سند Pinecone، Qdrant یا فروشنده‌ای دیگر را اضافه/تصویب نمی‌کند.
- Agent، RAG و MCP به‌طور پیش‌فرض محصولات عمومی نیستند؛ فقط موردِ بازبینی و منتشرشده می‌تواند endpoint مصرفی/محصول قابل‌فروش شود.

## ۶. SaaS، AIaaS و AaaS در موقعیت هادیران

| لایه | چه چیزی ارائه می‌دهد؟ | کاربرد محتمل در هادیران |
|---|---|---|
| **SaaS** | برنامه‌ای که انسان با آن کار می‌کند؛ پلتفرم و فضای مدیریت | حساب، `/workspace`، کاتالوگ، خرید، آزمون‌ساز و کنترل عامل‌ها |
| **AIaaS** | قابلیت/مدل AI به‌صورت API یا SDK | زیرساختی که runtime برای inference یا پردازش مصرف می‌کند؛ ممکن است از تأمین‌کنندهٔ بیرونی باشد |
| **Agent-as-a-Service** | Agentی که کار چندمرحله‌ای تعریف‌شده را انجام می‌دهد و خروجی مشخص تحویل می‌دهد | Agentهای هادیران که پس از ارزیابی، به‌صورت API یا تجربهٔ کاربری عرضه می‌شوند |
| **Workflow/Agent builder** | محیطی برای ساخت، تنظیم و پایش جریان‌ها و Agentها | ابزار کنترلِ مالک در هادیران؛ خودِ builder لزوماً AaaS نیست |

تعریف IBM از AIaaS بر تحویل ابزارها/قابلیت‌های AI از cloud و دسترسی API/SDK تأکید می‌کند؛ این را از فروش یک نتیجهٔ کامل توسط Agent جدا نگه می‌داریم. [IBM: AI as a Service](https://www.ibm.com/think/topics/ai-as-a-service-aiaas)

## ۷. دامنه‌های منطقی و راهبرد استقرار

### ماژول‌های پیشنهادی در یک برنامهٔ ماژولار

1. هویت و دسترسی.
2. آزمون‌سازی و محتوای pack.
3. اجرای آزمون، نتیجه و تحویل تفسیر/سند.
4. کاتالوگ و عرضه‌ها.
5. سفارش، پرداخت و دفتر مالی.
6. Entitlement و Usage.
7. رجیستری و کنترل Workflow/Agent/RAG.
8. اتصال‌های MCP مستقل.
9. فروشگاه عمومی و fulfillment خودش.

هر ماژول API عمومی خودش را دارد؛ خواندن مستقیم جدول داخلی ماژول دیگر، راه ادغام نیست. تیم/نیاز عملیاتیِ مستقل، مقیاس یا الزام جداسازی می‌تواند بعداً استخراج یک ماژول را توجیه کند.

در این مرحله microserviceهای متعدد توصیه نمی‌شوند: مرزهای کسب‌وکار در حال تثبیت‌اند، و تراکنش سفارش/پرداخت/دسترسی به صحت و idempotency نیاز دارد. راهبرد مناسب فعلاً **ماژولار در یک برنامه، با امکان استخراج بعدی** است. Fowler بر شروع با monolith ماژولار و استخراج پس از روشن‌شدن مرزها تأکید می‌کند؛ Shopify نمونهٔ مرزبندی دامنه‌ها با رابط‌های عمومی در یک کدبیس است؛ راهنمای Azure هم استخراج سرویس را از bounded context و مدل دامنه آغاز می‌کند. [Fowler: Monolith First](https://martinfowler.com/bliki/MonolithFirst.html) · [Shopify: Deconstructing the Monolith](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) · [Azure: Domain Analysis](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)

این تصمیم **MCP را از ابتدا remote** بودنش مستثنا نمی‌کند؛ آن قید پیشین همچنان پابرجاست. «همهٔ سرویس‌های منطقی باید API داشته باشند» با «هر API یک فرایند و پایگاه‌دادهٔ جداست» برابر نیست.

## ۸. قیدهای مرزی و وضعیت مخزن فعلی

- مدل مشترک تجاری به معنی پل بین آزمون‌های غیر-Casio و Casio نیست. قید فعلی «Casio جدا و پل بین‌دامنه‌ای ممنوع» پابرجاست؛ این طرح Casio را به محصول/سفارش/اجرای آزمون‌های مورد بحث وصل نمی‌کند.
- در مخزن فعلی `shop_listings/shop_orders` و `assessment_tariffs/assessment_orders` دو جریان جدا هستند. گزارش فعلی `loadFinance()` سفارش فروشگاه را می‌خواند و گزارش یکپارچهٔ هر دو جریان نیست.
- شناسهٔ خدمت آزمون در قرارداد فعلی از `slug:service` ساخته می‌شود و به‌تنهایی رکورد Product واقعی نیست؛ مدل هدف باید این هویت را با محصول/عرضهٔ نسخه‌دار و رابطهٔ FKدار جایگزین/تکمیل کند، نه اینکه تاریخچهٔ سفارش را بازنویسی کند.
- مسیر افزونه‌های آزمون هنوز از `attemptKind + attemptId` استفاده می‌کند و تفسیر/سند Casio را جداگانه پشتیبانی می‌کند؛ خدمت اجرای قیمت‌دار فقط آزمون‌ساز عمومی را می‌پذیرد و Casio را رد می‌کند. این تغییر پل بین‌دامنه‌ای نمی‌سازد.
- قواعد ریال/تومان، کارمزد، گردکردن، coupon binding، ledger، تحویل و برگشت مصوب تغییر نمی‌کنند. پلن آزمون‌ساز و فروش آزمون هم از نظر فروشنده/درآمد دو نوع معامله‌اند؛ قواعد سهم/تسویهٔ یکی به دیگری تعمیم داده نمی‌شود.
- **بازبینی OmniArch (۲۰۲۶-۱۱-۰۵):** مخزن قابل‌خواندن شامل README، یک نمونهٔ FastMCP به نام `business_architecture_mcp_server.py`، `requirements.txt`، `.gitignore` و لایسنس است؛ برخلاف درخت پیشنهادی README، فایل‌های `docs/architecture_details.md` و `legal_framework.md` یا یک ontology/ledger اجرایی در مخزن نبود. README جریان مفهومی پنج‌ایستگاهی Gateway → Regulatory → Logic → Ledger → Observers و idempotency/یکپارچگی دفتر را پیشنهاد می‌کند. بنابراین فقط اصل مرزبندی جریان و حفاظت تراکنشی را به‌عنوان الهام عمومی می‌گیریم؛ ابزار Python خودش مرجع محاسبات مالی تولیدی نیست.
- **عدم اقتباس بدون تصمیم:** Utility Token، قیمت‌گذاری شناور هنگام مصرف، RWA، تفکیک مالیاتی، ادعای حقوقی/رگولاتوری و کیف‌پول/استراتژی نقدشوندگی در README پیشنهادهای وابسته به مدل کسب‌وکار و حوزهٔ قضایی‌اند؛ به Hadiran منتقل نمی‌شوند و قواعد مالی مصوب را تغییر نمی‌دهند.
- **برش پیاده‌سازی جاری:** اجرای آزمونِ آزمون‌ساز عمومی، همراه نتیجهٔ پایه و با تعرفهٔ مثبت/فعال، یک‌بار برای هر `attempt` فروخته می‌شود؛ تعرفهٔ تعریف‌نشده به رایگان تبدیل نمی‌شود و Casio از اجرای قیمت‌دار جداست. تفسیر و سند عرضه‌های مستقل‌اند.
- **اشتراک آزمون‌ساز:** پلن فروشگاه تعداد، مدت و سیاست تمدید را تنظیم می‌کند؛ سفارش هر سه مقدار را snapshot می‌کند، فعال‌سازی در تأیید دریافت طبق سیاست انتخاب‌شده انجام می‌شود و ساخت pack/کاهش سهمیه در یک تراکنش ثبت می‌شود. مالک سهمیه نمی‌خواهد؛ ویرایش pack سهمیه مصرف نمی‌کند.
- migration جدید فقط فایل‌محور ساخته شده و هنوز اجرا نشده است. هیچ endpoint یا payload بیرونی برای Agent/RAG حدس زده یا فراخوانی نشده؛ Agent عمومی نیست. قواعد مالی مصوب تغییر نکرده‌اند و قفل تراکنشی `src/lib/finance/ledger.ts` نیز حفظ شده است.

## ۹. مواردی که هنوز نیاز به تصمیم/تنظیم دارند

تصمیم‌های دامنهٔ آزمون‌ساز و عرضه‌ها تثبیت شده‌اند؛ قیمت/محدودیت نامشخص، رایگان یا نامحدود فرض نمی‌شود:

1. **مقادیر پلن آزمون‌ساز:** قیمت، تعداد ساخت، مدت و سیاست تمدید (شروع فوری یا پس از پایان دورهٔ جاری) هر listing را مالک صریحاً تنظیم می‌کند؛ تا آن زمان آن listing فعال/قابل‌خرید نیست.
2. **تعرفهٔ اجرا و افزونه‌ها:** قیمت‌های اجرا، تفسیر و سند و تنظیمات مالیِ هر تعرفه باید از میز موجود تکمیل و فعال شوند؛ اجرای پایه و نتیجهٔ همان نوبت یکی‌اند، تفسیر و سند مستقل.
3. **قرارداد runtime بیرونی:** hostname/endpoint، احراز هویت، payload/response، timeout، retry/idempotency، logging و retention باید از ارائه‌دهنده مشخص شود؛ تا آن زمان فراخوانی خاموش است.
4. **عامل‌ها:** عامل فعلاً داخلی و owner-only می‌ماند. ابزارها، سیاست تأیید، دسترسی داده و هر نوع انتشار یا قیمت مصرفی قبل از بازشدن برای دیگران جداگانه تصویب می‌شود.

## ۱۰. وضعیت اجرا و گام‌های باقی‌مانده

1. Vertical slice اجرای آزمون قیمت‌دار و اشتراک آزمون‌ساز پیاده‌سازی شده است؛ migration `0035_assessment_authoring_subscriptions.sql` و رجیستری آن تولید شده‌اند.
2. Migration و DB عمداً اجرا/تغییر داده نشده‌اند؛ کاربر آن را پس از push اجرا می‌کند. تا آن زمان هیچ listing اشتراکی را برای فروش منتشر نکنید.
3. پیش از عرضه، مالک باید قیمت، سهمیه و مدت listing اشتراک و تعرفه‌های مثبت/کامل اجرا، تفسیر و سند را صریحاً پیکربندی و فعال کند.
4. پس از migration، smoke test خرید → تأیید دستی → فعال‌شدن دوره → مصرف هم‌زمان سهمیه و مسیرهای پرداخت/تسلیم اجرای آزمون لازم است؛ مسیر Casio و add-onهای مستقل نیز باید جدا بمانند.
5. Agent/RAG/runtime همچنان پشت مرز owner-only و fail-closed است. مرحلهٔ بعد برای اتصال، دریافت قرارداد بیرونی است؛ endpoint، credential، payload یا policy را حدس نزنید.
6. پس از روشن‌شدن runtime و نیاز عملیاتی واقعی، استخراج احتمالی به سرویس مستقل بررسی می‌شود؛ microservice پیش‌شرط مدل محصول نیست.
