## ۰. اول تشخیص: چرا وضع فعلی «درهم» است؟

حق با کاربر است. آنچه در دور قبل ساخته شد (`mcp_configs` تک‌ردیفه + `/workspace/mcp`) سه چیز متفاوت را در یک جدول و یک صفحه قاطی کرده:

| چیزی که قاطی شده | ماهیت واقعی‌اش |
|---|---|
| حالت لوکال/LLM، کلید مدل، temperature | تنظیمات **موتور مصرف‌کننده** (چت خانه)، نه MCP |
| سطح دادهٔ مخاطب و وزن‌های بازیابی | **سیاست یک مصرف‌کننده** خاص، نه ویژگی سرویس MCP |
| توکن اندپوینت بیرونی و روشن/خاموشش | تنظیمات **انتشار یک سرور** است، نه کل سرویس |

یعنی الان «یک MCP با یک تنظیم سراسری» داریم؛ چیزی که کاربر می‌خواهد این است:

```text
سرویس MCP (لایهٔ کنترل و رجیستری)
└── چند MCP مستقل (هرکدام هویت، تنظیمات و اطلاعات خودش)
    └── داخل هر MCP: ابزارها، پارامترها، مقادیر، منابع و پرامپت‌ها — همه قابل کنترل
```

این سند اول معماری خود MCP و الگوهای کنترلش در دنیا را جمع می‌کند، بعد ساختار بخش‌بندی‌شدهٔ هادیران را پیشنهاد می‌دهد.

## ۱. منبع حقیقت چه می‌گوید؟ (رادار ۳۴)

رادار روی MCP حکم «احتیاط» داده و این برای طراحی ما چهار پیام مستقیم دارد:

**الف) «MCP به‌مثابه پیش‌فرض» — حلقهٔ احتیاط (ورودی ۴۰).** رادار هشدار می‌دهد MCP را لایهٔ پیش‌فرض هر یکپارچه‌سازی نکنیم. MCP وقتی ارزش واقعی دارد که «قراردادهای ابزاری ساخت‌یافته، مرزهای احرازهویت مبتنی بر OAuth و دسترسی چندمستأجری حکمرانی‌شده» لازم باشد؛ وگرنه «مالیات انتزاع» می‌دهد: هر لایهٔ پروتکلی میان ایجنت و API از وفاداری کم می‌کند. حتی یک CLI خوش‌طراحی با خروجی JSON اغلب کافی است.
← **نتیجه برای هادیران:** لایهٔ MCP را برای *تعریف، حکمرانی و انتشار بیرونی* می‌خواهیم؛ مصرف‌کننده‌های داخلی (چت خانه) لازم نیست برای هر فراخوانی از روی پروتکل بپرند — مالیات انتزاع را داخل خانه نمی‌پردازیم. پروتکل برای مرز بیرونی و حکمرانی است.

**ب) مهندسی بافت و بازیابی پویا (تم‌ها + ورودی ۱).** رادار «مهندسی بافت» را در حلقهٔ پذیرش می‌داند و صریح می‌گوید بازیابی پویا یعنی «ابزارها را برمی‌گزیند و فقط سرورهای MCP لازم را بار می‌گذارد تا بافت بی‌جهت باد نکند».
← **نتیجه:** سرویس باید بتواند برای هر مصرف‌کننده فقط زیرمجموعهٔ لازم ابزارها را عرضه کند (ترکیب مجازی)، نه اینکه همهٔ ابزارها همیشه در بافت مدل بریزند.

**ج) امنیت ایجنتی: سه‌گانهٔ مرگبار و مسمومیت ابزار (تم «رام کردن ایجنت‌های دسترسی‌خواه» + ورودی ۳۲ و ۷۷).** دسترسی به دادهٔ خصوصی + محتوای نامطمئن + اقدام بیرونی = سطح حمله. «تحلیل جریان سمّی» و اسکن امنیتی کامپوننت‌ها (از جمله سرورهای MCP و سکرت‌های هاردکدشده) توصیهٔ رادار است؛ اعتماد صفر و کمترین دسترسی بدیهی‌اند.
← **نتیجه:** هر ابزار باید سطح ریسک، نوع دسترسی (فقط‌خواندنی/مخرب) و وضعیت بازبینی امنیتی داشته باشد؛ چیزی بدون بازبینی «فعال» نمی‌شود.

**د) اکوسیستم در حال بلوغ است، نه تثبیت‌شده.** «MCP Apps» (ورودی ۵۷، نخستین اکستنشن رسمی؛ طرح `ui://` برای رابط‌های HTML داخل مکالمه) هنوز در حلقهٔ **ارزیابی** است؛ توزیع نسخه‌دار MCPها از راه بازارچه‌های افزونه (ورودی ۷۲) تازه شکل گرفته؛ و گرایش به مهارت‌ها (Skills) به‌مثابه بدیل کنترل‌شده‌تر (ورودی ۲۸) نشان می‌دهد MCP تنها راه نیست.
← **نتیجه:** ساختار داده باید نسخه‌دار و قابل تکامل باشد؛ روی اکستنشن‌های نابالغ (مثل MCP Apps) از الان سرمایه‌گذاری سنگین نمی‌کنیم.

## ۲. معماری خود MCP (مشخصات رسمی)

### ۲.۱ شرکت‌کننده‌ها: Host / Client / Server

MCP معماری client–host–server دارد: یک **Host** (کاربرد هوش مصنوعی مثل Claude یا چت خانهٔ ما) برای هر **Server** یک **Client** می‌سازد و هر Client اتصال اختصاصی‌اش را با همان سرور نگه می‌دارد؛ سرورهای محلی stdio معمولاً تک‌کلاینت و سرورهای راه‌دور Streamable HTTP چندکلاینت‌اند [1](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture).
سرورها مستقل و تخصصی‌اند: منابع/ابزار/پرامپت عرضه می‌کنند، باید قیود امنیتی را رعایت کنند و می‌توانند محلی یا راه‌دور باشند [3](https://modelcontextprotocol.io/specification/2026-07-28/architecture).

### ۲.۲ دو لایه: داده و انتقال

- **لایهٔ داده:** پروتکل JSON-RPC برای ارتباط، کشف نسخه و قابلیت (از جمله `server/discover`) و بدوی‌های اصلی (tools, resources, prompts و notificationها) [1](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture).
- **لایهٔ انتقال:** سازوکار جابه‌جایی پیام و برقراری اتصال و احراز هویت — دو انتقال استاندارد: **stdio** برای سرورهای محلی و **Streamable HTTP** برای سرورهای راه‌دور [12](https://www.bdemerson.com/article/model-context-protocol).

### ۲.۳ سه بدوی سرور — و اینکه هرکدام دست کیست

| بدوی | کی تصمیم می‌گیرد | ماهیت | متدها |
|---|---|---|---|
| **Tools** | مدل | تابع اجرایی (نوشتن، فراخوانی API، کوئری) | `tools/list`، `tools/call` |
| **Resources** | کاربرد (Host) | دادهٔ فقط‌خواندنی با نشانی URI برای بافت | `resources/list`، `resources/read` |
| **Prompts** | کاربر | قالب آمادهٔ تعامل (معمولاً اسلش‌کامند) | `prompts/list`، `prompts/get` |

این تفکیک «کی کنترل می‌کند» در همهٔ منابع یکسان است: ابزار دست مدل، منبع دست کاربرد، پرامپت دست کاربر [18](https://scalar.com/learn/mcp/what-is-mcp)، [25](https://modelcontextprotocol.io/docs/learn/server-concepts).

### ۲.۴ قابلیت‌های سمت کلاینت و چرخهٔ عمر

سرور می‌تواند از کلاینت چیز بخواهد: **Elicitation** (گرفتن ورودی/تأیید از کاربر وسط اجرا) فعال و مهم است؛ **Sampling** (استفاده از مدل هاست) و **Roots** در نسخهٔ ۲۰۲۶-۰۷-۲۸ منسوخ اعلام شده‌اند و پیاده‌سازی تازه نباید رویشان بنا شود [10](https://github.com/microsoft/mcp-for-beginners/blob/main/01-CoreConcepts/README.md)، [13](https://theairankings.com/guides/what-is-mcp/).
قابلیت‌ها با **مذاکره** مشخص می‌شوند: هر دو طرف قابلیت‌هایشان را اعلان می‌کنند (سرور: tools/resources/prompts/logging/completions؛ کلاینت: elicitation و…) و در کل تعامل باید به همان اعلان پایبند بمانند [24](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle).

### ۲.۵ دو نسخهٔ زندهٔ پروتکل — تصمیم فنی مهم

- **۲۰۲۵-۱۱-۲۵:** چرخهٔ `initialize` و نشست پروتکلی دارد؛ نسخهٔ مستقر در بیشتر کلاینت‌های امروز.
- **۲۰۲۶-۰۷-۲۸:** پروتکل **stateless** شده: هندشیک و `Mcp-Session-Id` حذف، هر درخواست نسخه و قابلیتش را در `_meta` حمل می‌کند، `server/discover` اجباری است و هدرهای `Mcp-Method`/`Mcp-Name` برای مسیریابی گیت‌وی‌ها آمده‌اند [12](https://www.bdemerson.com/article/model-context-protocol)، [16](https://www.descope.com/learn/post/mcp).
حکمرانی MCP هم از ۲۰۲۵-۱۲-۰۹ به Agentic AI Foundation زیر Linux Foundation رسیده و نسخهٔ جاری ۲۰۲۶-۰۷-۲۸ است [12](https://www.bdemerson.com/article/model-context-protocol).

← **نتیجه برای هادیران:** اندپوینت بیرونی فعلی ما (۲۰۲۵-۱۱-۲۵) برای سازگاری امروز درست است؛ ساختار داده باید «نسخهٔ پروتکل» را فیلد هر سرور نگه دارد تا مهاجرت به stateless بدون بازطراحی ممکن باشد.

### ۲.۶ احراز هویت

مشخصات برای سرورهای راه‌دور OAuth 2.1 را مبنا می‌گذارد و رادار هم دقیقاً همین را نقطهٔ قوت MCP می‌داند (مرزهای احرازهویت OAuth و دسترسی چندمستأجری حکمرانی‌شده). برای سرویس داخلی ما، توکن Bearer صاحب‌محورِ فعلی پل موقت است؛ ساختار باید جای فیلدهای auth (نوع، مرجع سکرت رمزنگاری‌شده، اسکوپ‌ها) را از اول داشته باشد.

## ۳. ساختار کنترل در دنیای واقعی: Control Plane + Registry + Gateway

جمع‌بندی اجماع صنعت (از جمله اجلاس MCP آوریل ۲۰۲۶) این است: **سطح کنترل MCP = گیت‌وی مرکزی + رجیستری**؛ رجیستری «منبع حقیقت واحدی است که سطح مجاز MCP را تعریف می‌کند و هر تصمیم اجرایی دیگر در برابر آن سنجیده می‌شود» و بدون کشف (Discovery) حکمرانی ممکن نیست [17](https://obot.ai/resources/learning-center/what-is-mcp-control-plane/).

الگوی مرجع مایکروسافت همین دوتایی را صریح می‌کند: یک **دیتا گیت‌وی** برای مسیریابی هر درخواست به نمونهٔ آمادهٔ سرور، و یک **سطح کنترل** برای مدیریت چرخهٔ عمر سرورها (استقرار، به‌روزرسانی، حذف) به‌همراه نقاط اتصال سازمانی مثل تله‌متری و کنترل دسترسی [1](https://microsoft.github.io/mcp-gateway/).
در الگوی Uber هم Registry سطح کنترل است (کاتالوگ صدها سرور و هزاران ابزار؛ منبع حقیقت کشف، مالکیت و فعال‌سازی) و Proxy Gateway سطح داده [14](https://www.uber.com/us/en/blog/designing-mcp-gateway/).
گیت‌وی دو چهره دارد: رو به ایجنت «سرور» است و رو به سرورها «کلاینت»؛ پس یک نقطهٔ منطقی واحد، کشف و مسیریابی و سیاست را پشت خود پنهان می‌کند [28](https://snehotoshbanerjee.medium.com/building-an-enterprise-mcp-gateway-a-system-design-perspective).

اجزای تکرارشوندهٔ سطح کنترل در همهٔ پیاده‌سازی‌ها:
- **رجیستری سرورها:** ثبت، کشف، متادیتا، مالک، وضعیت تأیید و دامنهٔ دسترسی هر سرور [7](https://www.truefoundry.com/mcp-gateway).
- **سرور مجازی (Virtual Server):** چیدن زیرمجموعه‌ای از ابزارهای چند سرور پشت یک اندپوینت، با کنترل دسترسی در سطح تک‌ابزار [2](https://github.com/agentic-community/mcp-gateway-registry).
- **سیاست و دسترسی ریزدانه:** RBAC تا سطح ابزار منفرد، احراز OAuth، و صدور اعتبارنامهٔ واسطه‌ای تا سکرت سرورها روی ماشین کاربر ننشیند [11](https://tyk.io/learning-center/mcp-gateway-architecture-technical-guide/).
- **حسابرسی و مشاهده‌پذیری:** لاگ هر فراخوانی با تصمیم سیاست و تأخیر؛ اسکن امنیتی هنگام ثبت و گیت fail-closed برای موارد ناامن [2](https://github.com/agentic-community/mcp-gateway-registry).

**رجیستری رسمی MCP** هم از سپتامبر ۲۰۲۵ در حالت preview زنده است [3](https://modelcontextprotocol.info/tools/registry/) — اما فقط کشف عمومی است و اجرای سیاستی ندارد؛ برای ما «الگوی قالب متادیتا» مهم است، نه وابستگی به آن.

## ۴. آناتومی یک MCP: «اطلاعات و تنظیمات هر سرور» چیست؟

قالب رسمی `server.json` رجیستری، حداقل آناتومی هویت یک سرور را تثبیت کرده است: `name` یکتا (مثل `io.github.user/server`)، `title`، `description`، `version`، مخزن، و نحوهٔ رسیدن به سرور — یا `packages` (نوع رجیستری، شناسه، نسخه، transport، آرگومان‌های پکیج و **متغیرهای محیطی**) یا `remotes` (نوع انتقال و URL، با متغیرهای قالب URL مثل `tenant_id` و `region` و انتخاب‌های مجازشان) [4](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/generic-server-json.md)، [5](https://modelcontextprotocol.io/registry/remote-servers).
متغیرهای محیطی هم در همین قالب ساختار دارند: نام، توضیح، این‌که سکرت است یا نه، اجباری است یا نه و مقدار پیش‌فرض [8](https://github.com/modelcontextprotocol/registry/blob/main/9afbaacdfdf8966d73de09a795076fb0386c5c3d/docs/reference/server-json/generic-server-json.md).

از دل گیت‌وی‌ها و رجیستری‌ها، رکورد کامل یک سرور در سطح کنترل این بخش‌ها را دارد:

```text
MCP Server
├── هویت: slug/name یکتا، عنوان، توضیح، نسخه، مالک
├── دسترسی: نوع انتقال (in-process | streamable-http | stdio)، نشانی/مرجع اجرا
├── احراز: نوع (none | bearer | oauth)، مرجع سکرت (فقط cipher+hint)، اسکوپ‌ها
├── قابلیت‌ها: tools/resources/prompts دارد یا نه + نسخهٔ پروتکل
├── سیاست انتشار: وضعیت (draft → in_review → active → disabled)، دیده‌شدن (internal | external)
├── دستور سرور (instructions): متنی که هاست هنگام اتصال به مدل می‌دهد
├── سلامت: آخرین بررسی، وضعیت، آخرین خطا
└── حکمرانی: بازبینی امنیتی، سطح ریسک، سازنده/تغییردهنده، زمان‌ها
```

نکتهٔ کلیدی: «تنظیمات هر MCP» با «تنظیمات سرویس» فرق دارد. سرویس فقط چرخهٔ عمر و سیاست کلان را نگه می‌دارد؛ هر سرور رکورد مستقل خودش را دارد.

## ۵. آناتومی ابزار و پارامتر: «کنترل گسترده» یعنی چه؟

تعریف ابزار در مشخصات دقیق است: `name` یکتا (۱ تا ۱۲۸ کاراکتر)، `title`، `description`، `inputSchema` و `outputSchema` (هر دو JSON Schema، پیش‌فرض دیالکت ۲۰۲۰-۱۲)، `annotations` و در نسخه‌های تازه `execution` [10](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

### ۵.۱ پارامترها = JSON Schema

`inputSchema` باید یک شیء JSON Schema معتبر باشد (نه null)؛ ابزاری که پارامتر ندارد صریحاً `{"type":"object","additionalProperties":false}` می‌گیرد [10](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).
پس «کنترل پارامترها» در سطح داده یعنی برای هر پارامتر این‌ها قابل تنظیم باشد: نام، نوع، توضیح (همان چیزی که مدل می‌خواند و پر می‌کند)، اجباری/اختیاری، **مقدار پیش‌فرض**، شمارش مجاز (enum)، کران‌ها (min/max/طول)، و الگو. و «مقادیر» در سطح سیاست یعنی: مقدار ثابت تحمیلی از سمت سرور، سقف (مثلاً `limit` هرگز بالای ۸ نرود)، و مقادیری که از زمینهٔ نشست پر می‌شوند نه از مدل.

### ۵.۲ Annotations: واژگان ریسک ابزار

مشخصات پنج نشانه تعریف می‌کند و همه **hint** هستند، نه تضمین [9](https://modelcontextprotocol.io/specification/2025-06-18/schema):

| نشانه | پیش‌فرض | معنا |
|---|---|---|
| `readOnlyHint` | false | ابزار چیزی را تغییر نمی‌دهد |
| `destructiveHint` | true | ممکن است حذف/بازنویسی کند (فقط وقتی readOnly=false معنا دارد) |
| `idempotentHint` | false | تکرار با همان ورودی اثر اضافه ندارد |
| `openWorldHint` | true | با جهان باز بیرونی (وب/API) طرف است، نه دامنهٔ بسته |
| `title` | — | نام نمایشی |

دو قاعدهٔ امنیتی مشخصات برای طراحی ما حیاتی است: همیشه باید انسانِ قادر به رد فراخوانی در حلقه باشد، و کلاینت‌ها باید annotations را **نامطمئن** بدانند مگر از سرور مطمئن آمده باشند [12](https://www.bdemerson.com/article/model-context-protocol).
← **نتیجه:** در سرویس ما annotations «اعلام سرور» است، ولی سطح ریسک نهایی را بازبینی انسانی در سطح کنترل تعیین می‌کند — دقیقاً همان تفکیک «اعلام» و «حکمرانی» که اسکن و تأیید رجیستری‌ها انجام می‌دهند.

### ۵.۳ خروجی و اجرا

اگر `outputSchema` اعلان شده، `structuredContent` پاسخ باید با آن منطبق باشد و کلاینت باید اعتبارسنجی کند [6](https://sunpeak.ai/blogs/claude-connector-tool-design/)؛ توصیه می‌شود کنار خروجی ساخت‌یافته، یک بلوک متن JSON هم برای سازگاری برگردد.
در سطح کنترل، برای هر ابزار این سیاست‌های اجرایی هم قابل تنظیم است: فعال/غیرفعال، timeout، سقف نرخ، نیاز به تأیید انسانی، و نقش‌هایی که حق فراخوانی دارند (RBAC تا سطح ابزار [11](https://tyk.io/learning-center/mcp-gateway-architecture-technical-guide/)).

## ۶. ساختار پیشنهادی برای هادیران (IA و مدل داده — هنوز بدون کد)

### ۶.۱ چهار لایهٔ بخش‌بندی

```text
لایه ۰ — سرویس MCP (سطح کنترل + رجیستری)        میز: /workspace/mcp (بازطراحی)
  │   چرخهٔ عمر، وضعیت‌ها، بازبینی، سلامت، حسابرسی فراخوانی‌ها
  │
لایه ۱ — MCPها (رکورد مستقل هر سرور)             mcp_servers
  │   هویت، انتقال، احراز، قابلیت، نسخه پروتکل، instructions، سیاست انتشار
  │
لایه ۲ — داخل هر MCP                              mcp_tools / mcp_resources / mcp_prompts
  │   ابزار: اسکیمای ورودی/خروجی، پارامترها و پیش‌فرض‌ها و سقف‌ها، annotations، ریسک، سیاست اجرا
  │   منبع: قالب URI، mime، سیاست خواندن        پرامپت: قالب و آرگومان‌ها
  │
لایه ۳ — مصرف‌کننده‌ها و بستن‌ها (Bindings)       mcp_bindings
      هر مصرف‌کننده (چت خانه، اندپوینت بیرونی، بات آینده) یک «سرور مجازی» می‌گیرد:
      کدام MCPها، کدام ابزارها، با چه سقفی — همان بازیابی پویای رادار.
      موتور LLM و سطح دادهٔ مخاطب مالِ مصرف‌کنندهٔ چت است، نه سرویس MCP.
```

### ۶.۲ سرورهای اولیهٔ پیشنهادی هادیران

| سرور | ابزارها/منابع | دیده‌شدن |
|---|---|---|
| `knowledge` (باغ دانش) | `search_knowledge` + منابع `hadiran://knowledge/{slug}` + پرامپت‌های دوحالته | داخلی + بیرونی |
| `ecosystem` (خانه) | `search_ecosystem`، `resolve_topic_graph` + منبع `hadiran://ontology/worlds` و `hadiran://topics/{slug}` | داخلی + بیرونی |
| `audience` (مخاطب) | `get_audience_context` | **فقط داخلی** — هرگز بیرونی منتشر نمی‌شود (سه‌گانهٔ مرگبار) |
| موتور چت | — | سرور MCP نیست؛ **مصرف‌کننده** است (تنظیمات LLM و مخاطب همین‌جا می‌ماند) |

### ۶.۳ سرنوشت ساخت فعلی

- `mcp_configs` تک‌ردیفه می‌شکند به: (الف) رکوردهای `mcp_servers`، (ب) تنظیمات مصرف‌کنندهٔ چت (نام تازه، همان فیلدهای LLM/مخاطب)، (ج) توکن بیرونی می‌رود زیر رکورد سرور منتشرشده.
- `/api/mcp` فعلی می‌شود «انتشار بیرونیِ بستن external»؛ ابزارهای داخلی چت سر جای خود (بدون پرش پروتکلی — مالیات انتزاع رادار).
- میز `/workspace/mcp` از «فرم یک تنظیم» به «رجیستری + ویرایشگر هر سرور + ویرایشگر ابزار/پارامتر + بستن‌ها + سلامت و حسابرسی» تبدیل می‌شود.

### ۶.۴ ترتیب ساخت پیشنهادی (بعد از تأیید)

۱. مدل دادهٔ سه جدول اصلی (`mcp_servers`، `mcp_tools`، `mcp_bindings`) + مایگریشن تازه و Fail-soft مثل قبل.
۲. رجیستری در میز: فهرست سرورها، ساخت/ویرایش رکورد سرور، وضعیت و سلامت.
۳. ویرایشگر ابزار و پارامتر داخل هر سرور (اسکیما، پیش‌فرض، سقف، annotations، ریسک، فعال/خاموش).
۴. بستن‌ها: سرور مجازی برای چت خانه و اندپوینت بیرونی؛ `/api/mcp` و ارکستریتور چت از روی بستن بخوانند.
۵. حسابرسی فراخوانی‌ها و بازبینی امنیتی (وضعیت تأیید هر ابزار، لاگ تماس).

## ۷. تصمیم‌هایی که قبل از ساخت لازم است

۱. **دامنهٔ انتقال:** سرورها فقط in-process + یک انتشار HTTP می‌مانند، یا از اول جای سرور راه‌دورِ واقعی (URL بیرونی به‌عنوان MCP upstream) هم در رکورد باشد؟
۲. **مالکیت تنظیمات چت:** قبول است تنظیمات LLM/مخاطب از «MCP» جدا و زیر «مصرف‌کنندهٔ چت خانه» برود؟
۳. **سطح حکمرانی:** وضعیت بازبینی (draft/in_review/active) و لاگ حسابرسی فراخوانی از فاز اول باشد یا فاز بعد؟
۴. **نسخهٔ پروتکل:** انتشار بیرونی فعلاً روی ۲۰۲۵-۱۱-۲۵ بماند (سازگاری) و فقط فیلد نسخه برای مهاجرت به ۲۰۲۶-۰۷-۲۸ stateless نگه داشته شود؟
