# سیستم طراحی هادیران

وضعیت: پیشنهاد بررسی‌شده؛ بنیاد UI مرحله ۱ برای خانه و پوسته اصلی اجرا شده است
نسخه: 1.0

## 1. زمینه محصول

- محصول: اکوسیستم گفتگومحور فارسی برای شفاف‌سازی مسئله، بازیابی دانش و اتصال ایده به پروژه و دوره.
- خانه (`/`) لندینگ آماری نیست؛ خودِ گفتگو نقطه ورود اصلی است.
- مخاطب: فارسی‌زبانانی که با معماری سیستم، هوش مصنوعی، هستی‌شناسی، اتوماسیون و وب۳ کار می‌کنند.
- زبان و جهت: فارسی، `fa-IR`، راست‌به‌چپ.
- پشته تثبیت‌شده: Next.js App Router، React، TypeScript، Tailwind CSS 4، PostgreSQL و Drizzle.
- قیدهای فنی: وابستگی جدید اضافه نشود؛ انیمیشن پرتره فقط با WAAPI؛ مسیرهای native SVG حفظ شوند؛ grid و قطعه‌های مستطیلی جایگزین نشوند.

## 2. تصمیم طراحی

### جهت بصری

جهت منتخب «AI-native آرام و تحریریه‌ای» است:

- رابط باید بیشتر شبیه یک میز کار فکری و نقشه دانش باشد تا صفحه تبلیغاتی.
- ساختار مینیمال و خوانا، با فضای خالی کنترل‌شده و سلسله‌مراتب روشن.
- سیگنال‌های هوش مصنوعی با رنگ و جزئیات محدود نشان داده شوند، نه با پس‌زمینه گرادیانی سنگین، شیشه‌نمایی فراگیر یا نورپردازی نمایشی.
- پرتره عنصر هویتی و تعاملی است؛ نباید با کارت‌ها، سایه‌ها یا تزئینات پرتحرک با آن رقابت شود.
- تنها یک اقدام اصلی در هر نما وجود داشته باشد. در خانه، آن اقدام «نوشتن مسئله و ارسال آن» است.

### چیزهایی که ذخیره یا اعمال نمی‌شوند

- نتیجه‌ای که محصول را به اکوسیستم شارژ خودرو نسبت داده بود، نامرتبط تشخیص داده شد.
- جفت فونت عبری به‌دلیل نامتناسب بودن با مخاطب فارسی رد شد.
- الگوی Hero-Centric به‌عنوان الگوی اصلی خانه رد شد؛ خانه باید conversation-first بماند.
- پیشنهادهای GSAP ذخیره یا اجرا نمی‌شوند.
- رنگ‌های نئونی برای متن، گرادیان تمام‌صفحه و glassmorphism به‌عنوان هویت پیش‌فرض پذیرفته نیستند.

## 3. توکن‌های بصری پیشنهادی

این توکن‌ها مبنای مرحله اجرای بعد هستند؛ هنوز در CSS اعمال نشده‌اند.

### رنگ

| توکن | مقدار | کاربرد |
|---|---|---|
| `--color-bg` | `#F8FAFC` | سطح اصلی روشن |
| `--color-surface` | `#FFFFFF` | کارت، پیام و ورودی |
| `--color-fg` | `#0F172A` | متن اصلی |
| `--color-muted-fg` | `#475569` | متن توضیحی با کنتراست کافی |
| `--color-border` | `#CBD5E1` | مرزهای کم‌تأکید |
| `--color-primary` | `#4F46E5` | ارسال، لینک فعال و تمرکز |
| `--color-primary-on` | `#FFFFFF` | متن روی primary؛ نسبت کنتراست حدود 6.29:1 |
| `--color-cyan` | `#0891B2` | نشانه تعامل و داده؛ برای متن فقط با رنگ تیره روی آن |
| `--color-cyan-on` | `#0F172A` | متن روی cyan؛ نسبت کنتراست حدود 5.70:1 |
| `--color-green` | `#16A34A` | موفقیت یا وضعیت مثبت؛ متن سفید روی آن مجاز نیست |
| `--color-dark-bg` | `#0B1020` | سطح اصلی تاریک |
| `--color-dark-fg` | `#E2E8F0` | متن اصلی تاریک؛ نسبت کنتراست حدود 15.36:1 |
| `--color-danger` | `#DC2626` | خطا و اقدام مخرب |

قواعد:

- متن عادی حداقل نسبت 4.5:1 داشته باشد؛ متن بزرگ حداقل 3:1.
- cyan، بنفش روشن و سبز روشن برای تزئین یا پس‌زمینه کنترل‌شده هستند، نه متن کم‌کنتراست.
- رنگ تنها حامل وضعیت نباشد؛ متن، آیکن یا الگوی مکمل هم ارائه شود.
- سایه و blur کم‌هزینه باشند و برای تشخیص مرز به‌تنهایی استفاده نشوند.

### تایپوگرافی

- فونت موجود `Vazirmatn` به‌عنوان انتخاب محصول حفظ می‌شود؛ به فونت یا وابستگی جدید نیاز نیست.
- عنوان صفحه: وزن 700 یا 800، اندازه سیال، طول خط کوتاه.
- متن بدنه: وزن 400 یا 500، `line-height` حدود 1.65 تا 1.85.
- متن خواندنی: عرض حدود 65 تا 75 کاراکتر (`max-w-prose`).
- اعداد، کد و slugها با توجه به خوانایی از شکل لاتین یا فارسی مناسب همان محتوا استفاده کنند.
- از بیش از سه وزن فونت در یک نما استفاده نشود.

### فاصله و سطح

- واحد پایه: 4px؛ فاصله‌های اصلی از مقادیر 8، 12، 16، 24، 32 و 48px ساخته شوند.
- شعاع کنترل‌ها: 12px؛ شعاع پنل گفتگو: 16 تا 20px؛ از قرص‌سازی همه عناصر پرهیز شود.
- عرض محتوای تعاملی: حداکثر 80rem؛ متن مستقل: حداکثر 75ch.
- ارتفاع کنترل لمسی در موبایل حداقل 44px و فاصله کنترل‌های مجاور حداقل 8px باشد.

## 4. الگوی صفحه

### ناوبری

- ناوبری اصلی به جهان‌های اکوسیستم وصل می‌شود؛ موضوعات و تماس در footer یا مسیرهای ثانویه می‌مانند.
- حالت فعال با متن، پس‌زمینه و نشانه قابل تشخیص باشد.
- منوی موبایل باید دکمه 44px یا بزرگ‌تر، focus واضح و بستن قابل پیش‌بینی داشته باشد.
- محتوای sticky نباید focus را بپوشاند؛ برای اسکرول از `scroll-padding` استفاده شود.

### گفتگو

- ورودی از ابتدا فعال بماند، حتی هنگام مونتاژ پرتره.
- ورودی label قابل دسترس داشته باشد؛ placeholder جای label را نمی‌گیرد.
- وضعیت ارسال، انتظار، خطا و پاسخ موفق باید برای کاربر و فناوری کمکی قابل فهم باشد.
- پنل پیام فضای اسکرول مستقل داشته باشد، اما focus و پیام تازه نباید پنهان شوند.
- ارجاع‌های پاسخ به‌صورت گروه‌های قابل تشخیص و قابل کلیک ارائه شوند.

### پرتره

- هر path native SVG یک قطعه قابل scatter و assemble است.
- لایه قطعه‌ها و تصویر نهایی می‌توانند crossfade شوند، اما همه انیمیشن‌های پرتره با WAAPI اجرا شوند.
- انیمیشن اولیه فقط یک بار در همان session اجرا شود.
- پس از assemble پرتره ثابت بماند؛ کلیک کاربر replay را فعال کند.
- در `prefers-reduced-motion: reduce` پرتره مستقیم به حالت ثابت برود و scatter/replay متحرک اجرا نشود.
- fallback بدون WAAPI باید حالت ثابت بدهد، نه transition یا animation CSS.

## 5. تعامل و دسترس‌پذیری

- همه لینک‌ها، دکمه‌ها و ورودی‌ها focus-visible روشن و غیرقابل اشتباه داشته باشند.
- focus با header، footer یا پنل چسبان پوشانده نشود.
- برای عملیات طولانی `aria-busy` و پیام وضعیت پایدار ارائه شود؛ spinner نباید تنها بازخورد باشد.
- خطا کنار همان کنترل و با متن راه‌حل‌محور نمایش داده شود.
- کنترل‌هایی که فقط آیکن دارند نام accessible داشته باشند.
- hover تنها مسیر کشف یا استفاده نباشد.
- متن پاسخ طولانی با عرض محدود و فاصله خط مناسب نمایش داده شود.
- motion باید قابل توقف، کوتاه و هدفمند باشد؛ بیشتر از یک یا دو ناحیه کلیدی در هر نما هم‌زمان متحرک نشود.

## 6. رفتار responsive

| عرض آزمون | تصمیم اصلی |
|---|---|
| `375px` | تک‌ستونه؛ chat و ورودی بدون فشردگی؛ پرتره کوچک اما کامل؛ کنترل‌ها حداقل 44px |
| `768px` | افزایش فضای پیام؛ nav موبایل هنوز قابل استفاده؛ فاصله‌ها به مقیاس میانی برسند |
| `1024px` | شروع چیدمان دو ناحیه‌ای؛ متن و پرتره در کنار هم، گفتگو بدون رقابت با آن‌ها |
| `1440px` | محدودیت عرض حفظ شود؛ فضای خالی افزایش یابد، نه اینکه متن بیش از حد کشیده شود |

برای موبایل از `dvh` در ناحیه‌های وابسته به viewport استفاده شود و هیچ media یا badge بدون فضای رزروشده وارد layout نشود.

## 7. قواعد React و Next.js

- Server Component پیش‌فرض بماند؛ `use client` فقط برای chat، nav تعاملی و پرتره استفاده شود.
- برای تصاویر عادی از قابلیت بهینه‌سازی Next استفاده شود؛ پرتره native SVG به‌دلیل نیاز به path-level interaction یک استثنای مستند است.
- SVG جدید با 1603 path از یک source canonical ساخته می‌شود و در bundle جاوااسکریپت کپی نمی‌شود.
- refها، seedها و ثابت‌های path بیرون از چرخه render نگه داشته شوند.
- memoization فقط پس از مشاهده هزینه واقعی render انجام شود.
- برای مسیرهای کند `loading.tsx` و فضای رزروشده استفاده شود تا layout shift رخ ندهد.
- fetch سمت مرورگر با URL نسبی انجام شود؛ به localhost در کد browser-facing وابسته نباشد.

## 8. pipeline asset پرتره

- source اصلی: `assets/portrait/hadiran-portrait.source.svg`.
- خروجی runtime: `public/hadiran-portrait.svg` با id مستقل برای هر path.
- metadata کلاینت فقط viewBox و تعداد pathها را نگه می‌دارد؛ رشته‌های `d` وارد TypeScript نمی‌شوند.
- component از همان فایل با `<use href="/hadiran-portrait.svg#portrait-piece-0000">` استفاده می‌کند.
- تصویر نهایی و piece reference از یک asset مشترک استفاده می‌کنند تا geometry دوباره در bundle کپی نشود.
- تولید tile، grid، bbox culling و فایل `tiles.generated.ts` از pipeline حذف شده‌اند.
- build باید deterministic باشد و timestamp داخل فایل generated قرار نگیرد.

## 9. معیار پذیرش پیش از تحویل

- typecheck و lint بدون خطای تازه.
- بررسی دستی در 375، 768، 1024 و 1440px.
- بررسی keyboard-only، focus-visible، screen reader label و reduced motion.
- بررسی کنتراست متن و کنترل‌ها در light و dark.
- بررسی اینکه input از لحظه ورود فعال است.
- بررسی اینکه animation اولیه فقط یک بار در session اجرا می‌شود.
- بررسی اینکه portrait از native pathها استفاده می‌کند و هیچ grid یا مستطیل tessellation وارد نشده است.
- بررسی اینکه replay فقط با کلیک انجام می‌شود و حالت assemble نهایی ثابت می‌ماند.
- بررسی performance با توجه به 1603 path و نبود layout shift.

## 10. منشأ تصمیم‌ها

این سند با workflow repository `ui-ux-pro-max-skill` تهیه شده است: تشخیص stack، یک design-system query، queryهای outcomeمحور برای UX و queryهای stack-specific. فقط خروجی‌هایی که با محصول، مخاطب، RTL فارسی و قیدهای فنی هادیران سازگار بودند نگه داشته شدند. این سند قبل از اجرای تغییرات UI نیازمند تأیید مرحله‌ای است.
